## 一、结论（先说三条，与"顺手清黄"的直觉相反）

1. ⛔ **不建议为"清黄"而拆。** 黄是**提示**不是闸门（你 2026-09-21 亲自把 >600 从"禁合入"降成黄，
   理由写着「**行数是代理指标**」）—— 而**它的反面实测成立**：本仓**拆完会再长回来**，
   三例、全在两周内：
   | 件 | 拆后 | 现在 | 回潮 |
   |---|---|---|---|

   | `tools/probe/_shell_smoke.py` | 598 → **530**（2026-09-21） | **578** | **+48** |
   ⇒ 「拆一次就永久变短」是**假预期**；行数是**代理**，不是目标。
2. ✅ **只拆同时满足 §四 六条判据的件**：**天然接缝**（能一句话说清两半职责）＋ **零行为变化**（整块搬运）＋
   **同批搬观测面**（读源码断言 / 变异锚点 / `chain_expected.txt` 的 `文件::函数` / 再导出）。
3. ⭐ **优先级：测试文件 ＞ 代码文件**。`@acc` 是**按用例号认领**的（实测：拆文件后 `--collect-only`
   条数不变）⇒ **拆测试不动判据**，成本最低、收益（定位 + 我的读成本）却真实。

## 四、六条裁决判据（建议作为 `细则 §廿一` 的补充）

1. **只对 >600 的件讨论"必须处理"**；400–600 默认"**登记 + 观察**"，⛔ 不为清黄动手。
2. **必须有天然接缝**（能一句话说清"这一半管什么、那一半管什么"）；说不清 ⇒ 不拆。
3. **必须整块搬运、零行为变化**（判定/文案/断言一字不变 ⇒ 四态零丢失）。
4. **观测面同批搬**（读源码断言 · `tools/mut/` 锚点 · `chain_expected.txt` · 再导出 + 守卫断言）。
5. **测试件优先**（不动判据）；代码件次之，壳件最后（`shell_verify` 逐件核对 ⇒ 另算）。
6. ⭐ **对我读成本真有改善**：判定标准是「**改一处要开的文件数**」——拆后变少 ⇒ 拆对；拆后一样多或更多 ⇒ 不拆。

### 按行业标准的**重裁**（这是"执行"的结论）

1. ✅ **那 28 个 `.py`：一条都不拆。** Python 侧行业线 = **1000**，我们最长 **578** ⇒ **没有任何一条触线**。
   本件 §五 里说的"优先做 9 条（测试件）"，含义只是「**若你非要清黄**，从它们下手最便宜」——
   **按行业标准，清黄这件事本身不成立** ⇒ **执行 = 不动**（0 次拆分）。
2. ⭐⭐ **真正超标的是壳**（JS 侧 300 行）—— 而这正是 §六.2 指出的**缺口**：`T5` 只扫 `.py`
   ⇒ **壳从来没被行数纪律看过**。按行业标准，该讨论拆分的地方是壳，⛔ 不是那 28 个 `.py`。
   ⚠️ 壳有两条**独特约束**，所以不能照搬 ESLint 的 300：
   - ✅ `shell_verify.py` 的不变量 = 「四件的并集 ⇄ 单文件壳**逐行多重集**一致」⇒ **拆分技术上安全**
     （读取点已收敛在 `shell_source` ✓）；
   - ⛔ 但 `V.<页>` 切片是**原型规格的复制**（`ui_parity` `U1` ＋ `U5` 双份真源）⇒
     **拆法必须避开切片与规格件**，只能动**壳自己的**部分（`API` · 取数缓存 · 动作）。
3. ⛔ 因此：**ESLint 的 300 不作为我们的处置线**（它是 lint 默认值，多数工程会按项目上调；
   而本项目壳的形态由"原型整体复制 ＋ 适配层"决定）。我们**保留 400 作观察线**，
   并把行业线（300 / 1000）**登记在 `docs/reference/thresholds.md` 作对照** —— 数字集中在一处，⛔ 不散进代码。
