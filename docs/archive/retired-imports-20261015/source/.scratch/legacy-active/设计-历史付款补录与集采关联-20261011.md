### 2.2 月表结构模型（8 张主表通用形态，P2 逐张验证）

```text
[区块标题行]   "XX（项目名） 项目YYYY年M月份付款计划（账面数：…）"     ← 特征：含"付款计划"、不含"外租机械"
[表头行]       科目 | 费用日期 | 材料：其他支出付资产处/贸易公司（编号） | 收款单位 |
               该流程金额 | 已付款金额 | 本月预付款金额 | 剩余付款金额 | 付款时间 | 付款方式 | 备注
[机械段说明行]  "外租机械：付款通知书 （编号）"                        ← 单格固定行，每区块必有
[数据行]×N     A=科目（材料费集采/材料付款/集采/外租机械费/空）
               B=费用日期（真日期 或 Excel 序列号如 46174）
               C=编号（FKTZS… / QTZC… / 空 / "小计：" / "合计："）
               D=收款单位（可能是"充油卡"这类非单位文本）
               E=该流程金额  F=已付款金额  G=本月预付款金额  H=剩余付款金额
               I=付款时间（部分表用）  J=付款方式  K=备注
               L（第 12 列，无表头）=实际付款批注："1.21付款" / "8.27付" / "8.14付" …
               N（部分行）=付款条件长文本（如"货到验收合格30±7天工作日"）
[小计：行]      C 列 = "小计："（数值行）
[合计：行]      C 列 = "合计："（**含 #REF! 公式损坏** —— 不得作为核对权威）
```

**边界算法（写进脚本，⛔ 不用旧行号）**：
区块切分 = 找所有"含『付款计划』的行"（标题锚点）→ 每个区块 = 本标题行到下一标题行之前。
标题自证异常（写"2月份"实际在 3 月表 81 行等**文字笔误**）不影响归属：**归属月份一律取 sheet 名**。
P2 必须为每张 sheet 产出**列映射表**（哪列是编号/金额/日期/批注），并把异常如实列出（如 3 月表首区块 1-17 行**无标题**）。

### 2.4 付款线索规则（继承用户前轮 9 条裁决 → 机器可执行版）

**候选的必要条件 = L 列（第 12 列）有可确证的具体日期**（形态："M.D付款"/"M.D付"/"YYYY.M.D"/"M月D号"），
且该行不是小计/合计/表头/机械段说明/区块标题。其余规则：

| # | 规则（来源＝用户前轮裁决） | 机器实现 |
|---|---|---|
| 1 | L 有日期＋显式金额（"付10万"）⇒ 用显式金额；L 有日期无金额 ⇒ 可用同一行 **G（本月预付款金额）** | 金额取用顺序：L 显式金额 → G；每次取用记 `amount_basis` |
| 2 | **不能把 G 当通用实付列**；用 G 必须多源核对一致 | 硬条件：本行 `E−F == G` **且** 与前/后月同名条目（同编号/同费用日期）的 E/F/G 演变自洽；不满足 ⇒ 待确认 |
| 3 | **E/G 整体错位**的区块隔离（8 月慧能即属此类） | 错位检测：区块内 `E−F` 与 `G` 的大面积不等（>30% 行）⇒ 整块升格为"待确认"并在报告点名 |
| 4 | F（已付款金额）只作历史佐证，**不凭 F 新造流水** | F 只进 `evidence` 字段，不单独生成候选 |
| 5 | 无编号（C 空）⇒ 允许按项目＋收款单位＋金额＋日期找**唯一**候选，**必须用户确认** | 进"待确认清单"，附候选匹配证据；⛔ 永不自动落库 |
| 6 | L 只有"√/已付/某月已付"无具体日 ⇒ 待确认，不自动导入 | 进"待确认清单" |
| 7 | 日期歧义（如"7.2"）⇒ 交叉验证（I 列、前后月、汇总表、库内流水）；不能确证 ⇒ 待确认 | 解析器产出 `date_basis`；歧义进"待确认清单" |

### 4.2 P2/P3 抽取与核对（票 285 的工作）

**P2 算法**：
1. 归档源文件（§2 开头）→ 记录 sha256。
2. 逐 sheet：找标题锚点（含"付款计划"）→ 切区块 → 逐张产出**列映射表**（编号列/金额列/日期列/批注列）。
3. 逐行分类（四类互斥、合计可复算）：
   - **候选**：L 有可确证日期 ＋ 不是小计/合计/表头/机械行/区块标题。
   - **排除**：汇总表全部行、8 月慧能/宜化整块、小计/合计行、区块标题、机械段说明行、空白行、负数/退回行。

   - **佐证**（不进候选/不退待确认）：F 非零但 L 无记录等"只作历史佐证"的行。
4. 产物 `artifacts/hist_supplement/extract/`：`抽取明细.jsonl`（每行：sheet/行号/区块/原文／分类/依据）＋
   `排除清单.csv` ＋ `待确认清单.csv` ＋ `列映射表.md`。

**P3 算法**（读库，`app.core.db.session_scope`，只读不写）：
1. 匹配：`bill_no` 精确 → 未命中进"未匹配清单"；无编号行做候选匹配（项目名＋收款单位＋金额），**列出候选供用户确认**。
2. 与现有流水比对（**不分来源**：含用户手工录入的与既有导入的）：同 `notice_id` ＋同金额＋同日期且 `status=effective` ⇒ 标"库内已有"⇒ 从候选剔除（并入排除报告）。

3. 集采关联检查：候选 ∈ 集采分类且未关联 ⇒ 进"**缺关联清单**"（交用户 P1 处理）。
4. 准入预检（复用 §3.2 判定，**在清单生成阶段就判**）：审批≠已批 / 撤单 / 剔除 ⇒ 进"待确认清单"（附原因）。
5. 超付模拟：同通知书按清单顺序累计（`已付 + 拟写` vs `审批金额`）⇒ 超出的笔进"**超付候选清单**"（须用户逐笔批准）。
6. 产物：`核对报告.json`（五张清单）＋ `缺关联清单.csv`。

```python
    """事务内逐笔复验＋写入 → {"batch", "written", "amount_total", "exceptions", "rows_written": [...]}
    任一"必须拒"行 ⇒ 抛 MustReportError（由外层 session_scope 整批回滚，不落半批）。"""
```

**复验规则表（逐笔；判定来源必须复用 §3.2，禁止在本文件重写判定）**：

| # | 规则 | 复用点 | 例外 |
|---|---|---|---|
| 1 | 通知书存在；`bill_no` 与清单一致 | — | 无 |
| 2 | 审批状态＝"已批" | `PayRow.block`（`BLOCK_STATUS`） | 无 |
| 3 | 未撤单（`i8_revoked`）、未剔除（`excluded`） | `NoticeRow` 字段 | 无（撤单有牵涉的行也不许静默动，走人工） |
| 4 | 集采分类 ⇒ 已关联（`has_link`） | `PayRow.block`（`BLOCK_JC_UNLINKED`） | 无（**不得绕过关联闸**） |
| 5 | 金额>0（分精度 `Decimal`） | `confirm_batch` ④ | 无 |
| 6 | 金额 ≤ 本次应付（`cap = 审批 − 已付`，**按批内序累积**） | `confirm_batch` ⑤ | 仅 `overpay_approved=true` 的已批准行放行，回执单列 |
| 7 | 方式：空 ⇒ 放行（存空）；非空 ⇒ ∈四类；"其他"须备注 | `confirm_batch` ⑥⑦；`_method_of` | 空方式＝既有历史导入口径（§4.4.6），回执报数 |
| 8 | 日期格式 `YYYY-MM-DD` 且 ≤ 清单生成日 | — | 无 |
| 9 | 防重三道：`has_request_id(HIST#{batch}#{seq})`；内容指纹（`notice_id+pay_date+amount`）对库内**生效**流水；批内指纹 | `has_request_id` | 无（命中即拒并报） |

**实现要点（给执行 agent 的硬约束）**：
- 逐笔判定用 **`confirm_batch([pay_row], {nid: PayDraft(pay_method=…, amount=…)}, pay_date=该笔日期)`** ——
  单行批 × 逐笔日期，天然兼容"历史每笔日期不同"（`apply_batch_pay` 的整批共用日期不适用，**但判定函数本身可复用**）。
- 例外放行**只在 confirm_batch 报错后做"错误分类"**：唯一错误 ∈ {超出本次应付} ⇒ 查 `overpay_approved`；
  唯一错误 ∈ {方式非法} 且 `method==""` ⇒ 查 `blank_method`；其他错误一律 blocked。分类代码写死这两类，⛔ 不做通用豁免框架。
- `project_id = 通知书.ownership_id`（`None` 照实写 `None`）——理由见 §5.1。
- `remark` 用清单里的来源串（可追溯）；`source=FLOW_SOURCE_IMPORTED`；`import_batch=batch`；`request_id=HIST#{batch}#{seq}`。
- **不写 `jc_payment`、不碰 `stat_paid`（由 `sync_stat_paid` 自动）、不发 HTTP、不改 ORM。**

**执行脚本**：`tools/oneoff/_hist_commit.py`（一次性操作脚本；读清单＋校验 sha256＋打印回执 JSON）。
**执行流程（P5）**：
1. `ops\server_ctl.ps1 -Action status` 记录服务状态 → `-Action stop`（停服窗口）。
2. 备份：`pg_dump` 按 `.env` 的 `DATABASE_URL` 输出到 `.artifacts/recovery/backups/YYYYMMDD-HHMM_历史补录写前/`（⚠️ 备份落点唯一在 `.artifacts/recovery/backups/`）。
3. `backend\.venv\Scripts\python.exe -X utf8 tools\oneoff\_hist_commit.py --plan <清单> --apply`
4. 复算（P6）→ 回执归档 → `-Action start`。
5. 任何一步失败：不写/回滚；已写入后发现错 ⇒ 用 `rollback_batch`（按批次整批撤销留痕）后重新走清单。

### 4.5 P6 独立复算验收（票 286 收尾）

**脚本**（新，只读）：`tools/probe/_hist_verify.py`。逐层复算，任一层不一致即报（不许以"写入成功提示"替代对账）：
1. **按笔**：清单 rows vs 库内 `payments_of(notice)` —— 金额/日期/方式/来源/批次/request_id 逐笔一致。
2. **按通知书**：`amount_paid`（生效流水合计）vs 清单预期；`stat_paid` 未手改者应相等；**手改者差异单列**（保护正确）。
3. **按项目**：`build_stats` 左栏/右栏 + `build_flows` 筛选复算。
4. **按集采合同**：`build_detail(contract).pay_sum` 前后差 == 该合同关联通知书的补录金额和。
5. **总账**：`payment_flow` 本批条数/金额 vs 回执；无本批以外的行被改动（对比备份或 WHERE 审计）。

## 五、关键口径决定（本设计稿拍板，理由随附）

### 5.1 `project_id` 写 **通知书 `ownership_id`**（不是 `None`）

- 现状：现有 `importer.commit` 写 `None`（历史遗留）⇒ 流水页"付款项目"列空白（`_flow_dict` 只认 `f.project_id`，§3.4），与用户要求
  "生成流水在 UI 中能正确显示所属项目"直接冲突。
- 决定：`supplement.py` 写 `ownership_id`（`None` 照实写 `None`）——**与正常付款链一致**（`apply_batch_pay` 写 `row.ownership_id`），
  是"读取归属事实"而非"修改归属"。
- 附注（不阻塞本票）：是否把现有 `importer.commit` 的 `project_id=None` 也统一为 `ownership_id`，属**行为变更**，
  由用户在 `TAIL-286` 开工时点一次头（改了要补一条回归断言）；本设计不强制。

### 5.2 超付：允许但仅限"用户逐笔批准的清单行"

沿用 §4.4.6 既有口径（历史流水照记、不封顶、不篡改事实）；"付款动作"链的禁超付**不动**。
超付行在 P3 就模拟出来（§4.2 P3-5）→ 用户在批准清单时逐笔点头 → P5 回执单列。

### 5.3 空付款方式：存空，不编造

既有 `_method_of` 对 `imported` 源已允许空；`importer.normalize_method` 的"空⇒空/认不出⇒其他＋原文留备注"口径沿用。
⛔ 不得把历史空方式兜成"现汇"（那是 `manual` 付款动作的默认值，两条口径互不干扰——`test_acc_flow_import.py` 已钉）。

### 5.4 批次与回滚

批次号 `IMP-HIST-YYYYMMDD`（重跑换 `-2` 后缀）。回滚＝既有 `rollback_batch`（整批撤销留痕）。不新建机制、不加审计表。

### 5.5 执行形态：脚本 + 停服窗口，不做 UI

理由：一次性回填（2026-01～2026-08），做完即退出；常驻 UI 会与 281/282/283 的壳改动打架且徒增维护面。
用户已定"统一预览→批准→一次性受控写入"——清单文件（+哈希）就是"预览"的载体。

### 5.6 「历史导入口要不要改」的取舍（用户 2026-10-11 问「改了有啥用」）

**现状**（本地实测）：历史导入口 = 通用导入面 → `m05_flow` 域（`imp_spec` → `importer` → `create_flow`）。
它**做对**的四件事：按单据号精确匹配 · 空方式存空 · 未匹配/异常逐条列出 · 批次整批回滚。
它**不做**的四件事（也正是本次补录必须补上的缺口）：
1. **不查集采关联闸**（§4.4.3）⇒ 现在直接上传一份五列表，就能把流水写到"未关联集采"的通知书上、绕过付款闸；
2. 不查审批状态 / 撤单 / 剔除 ⇒ 未批或已撤单的单据也能被写入流水；
3. 无内容级防重 ⇒ 同一笔付款换个批次可重复导入（只有"同批重导先整批回滚"这半条）；
4. `project_id` 恒 `None` ⇒ 流水页「付款项目」列空白。

**改了有什么用**：把上面 4 条补成"每次导入都自动过闸" = **从「一次性脚本」升级为「常驻安全入口」**；
判定仍只有一处（`mod03_notice.domain`），与正常付款共用 —— 以后任何补录都不必再临时写复核脚本。

**代价与风险**：动 `importer.py`/`imp_spec.py`（必须保留它既有的四件事口径：空方式、超付、整批回滚），
并补"现有导入用法不受损"的回归 ⇒ 属**行为变更**，得用户点头。

**本次的取舍**：本次**不改它** —— 补录走一次性适配器（`TAIL-286`），产出的清单格式与五列一致，将来若给导入口加闸可无缝复用。
建议：本次补录完成后**另立一小票**（如「历史导入口加三道闸＋归属＋防重」），⛔ 不作为本轮依赖。
