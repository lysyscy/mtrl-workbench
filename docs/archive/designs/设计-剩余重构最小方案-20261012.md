## 3. 选定的最小设计

### 3.1 所选付款事实（TAIL-310）

[助手自定] 在 notice_pay_actions 内部组装提交所需记录；外部 seam 仍为 apply_batch_pay / 既有 JSON 动作，不新建 HTTP interface。复用本包 get_notices_by_ids，以及 MOD05 service.flows_of_notices；关联继续经 MOD11 service.links_by_notice，给原出口增加可选 notice_ids，默认 None 保持全量列表行为，显式空列表直接回空。

查询只对唯一 ID 集合执行；结果重建 by_id 后按原 ids 重放。这样 SQL 返回顺序不影响付款顺序，重复 ID 仍按当前次数处理，missing 仍跳过，撤回/剔除仍排除；无剩余目标仍报当前错误。不借机去重、改成 missing 整批拒绝或修订排除回执。接口入参 ids 是 list[int]，当前 JSON 入口没有去重。

[交付面] 金额规则回 `delivery/材料科业务全流程说明书.md` §4.2.5 / §4.4.2–4.4.4，契约回 `delivery/PRD/02-功能规格/MOD-03.md`。应付 = 审批金额 − 生效流水实际合计，复用 effective_total；统计付款人工值不参与。保留 Decimal、分类空值兜辅材、审批判定、关联闸、默认付款方式、草稿 None/显式0的区别、request_id 及返回值。

[助手自定] 所选通知书、流水、关联与 create_flow 都用传入的同一 Session。全部 confirm_batch 成功后才写第一条；保持调用方事务回滚能力。此次不承诺新并发付款锁或跨请求原子幂等方案，列表展示/计划默认值取数亦保持原样。

### 3.3 当前错误与唯一横幅（TAIL-312）

[助手自定] FAILED 保持路名→人话的当前真源；另一个按同路名索引的技术 Map 与它同步。失败替换该路两半，成功删除该路两半。fails/failsTech 只由当前 Map 派生，BOOT_ERROR 保持字符串。覆盖 boot 并发的“当前登录用户”soft 路径；不能漏掉它，也不能成功一项就清掉其它失败项。

[助手自定] bootErrorBanner 使用稳定节点标识，存在则更新，当前无错则移除；保留 main 内 #view 前的布局流位置、人话、下一步和折叠技术明细。恢复要触发横幅同步，即使 BOOT_ERROR 已空也不能绕过移除。原有 pageState / retryPage 的逐页隔离保持。

[助手自定] 本票保持 LOADED 缓存、PENDING、LOAD_DEP 两组次序、ALWAYS_FRESH 的 m02 及写后 reload/markCrossPageStale。验收只保证串行失败→重试恢复，重复失败替换，横幅不重复；不宣称重叠请求“最后发出的获胜”，旧响应仍可能覆写错误和数据。复杂并发不能用本票成功作销号证据。
