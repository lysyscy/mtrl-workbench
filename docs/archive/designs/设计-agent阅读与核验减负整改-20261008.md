## 1. 已确认目标与授权

来源：用户 2026-10-08 本会话 Q1–Q12；已逐轮确认共享理解。本规格是本轮整改的唯一执行依据，不重启需求访谈。

目标是让 agent 按任务读对资料，按实际影响核验，避免被过期要求反复误导。文件数量和统一的一分钟限时不是目标；保留但不进入默认路径的资料可以继续存在。

用户确认整体范围和顺序后，agent 自主分批执行并报告。仓内外均纳入，现有目录骨架保持不变。业务行为变化、删除尚有现行用途的内容、范围外问题需要单独确认。提交须另获用户授权。

本规格的三阶段已按TAIL-251→252→253执行，结果回对应票与主计划§15；稳定流程回ops/agents/issue-tracker.md §四。本件退出日常路径，只在追溯整改依据或验收时读。不提交。

## 2. 判断原则

- 程序与真实运行说明现状；用户最新确认的需求决定目标。旧规格中的差距不自动变成补做任务，现有行为也不自动成为正确要求。
- 只报告与当前任务相关的口径冲突。业务选择未决时请用户判断；无关旧差距不阻挡交付。
- 现行文档保留当前要求和会影响修改的必要理由。实施流水、逐次改动、已解决事故退出正文；Git 已提供的历史不再人工复制。
- 不以历史日期或文件体量直接判定无用。一个已解决事故若仍影响安全修改，留下简短约束、触发条件和当前位置即可。
- 检查是否保留，看它保护的现行结果、损失后果和实际灵敏度。执行慢不是删除依据；过去曾经需要也不是永久保留依据。
- 阅读和核验选择必须可见，但不新增永久阅读日志、治理报表或另一套状态源。

## 4. 实施顺序

### 阶段一：统一阅读与核验流程

先处理会继续放大后续整改成本的规则和入口。

1. 保存当前 HEAD、已有 dirty 与文件字节基点，保留全部已有修改；本轮成果只计新增差异。凭据只记录校验值，不读取或输出内容。
2. 统一入口、流程主人、注入档及其指针中的冲突要求。核验流程只在 `ops/agents/issue-tracker.md` §四定义，其他文档按需指向它。
3. 取消“提交即全量”“文件新增/删除即全量”“既有未提交修改每轮重新全验”的无条件触发；保留相应真实影响判断。
4. 文档区分说明/索引、agent 操作规则、业务规格、机器消费输入。文件扩展名不证明低风险：修改被执行代码或测试实际消费的输入，需要验证对应使用者。
5. 未知影响先调查实际依赖并说明剩余不确定点，再选择检查；真正广泛共享影响才扩大。不能静默漏验，也不能把调查未完成直接等同全量测试。
6. 本轮更改选择器或检查机制，只验证受影响的选择分支、正常不误伤和能造出的漏验反例；不因此自动执行所有无关业务及元测试。
7. 自证优先在隔离夹具/副本中运行。正式工作区与仓外交付面不作临时变异靶；需验证真实实现时调用同一实现处理隔离输入，不能复制一份算法冒充覆盖。

完成标准：四个验收场景已有可用入口，旧全量指令不再出现在其有效阅读路径；新增检查不会形成新的一律触发规则。

### 阶段二：整理常读文档与仓外规格

范围由指针出发，不遍历阅读全部历史。

| 优先对象 | 整改重点 |
|---|---|
| `AGENTS.md`、`.codebuddy/memory/MEMORY.md` | 常驻内容只留每轮必要的入口/偏好/硬边界；任务专属内容用明确触发指针 |
| `.codebuddy/memory/细则.md`、`.codebuddy/memory/IDE-细节.md` | 同一概念的定义、约束、例外集中；事故流水退出；命令跟随当前入口 |
| 根 `README.md`、`ops/README.md`、`tools/README.md` | 地图先给用途和读取条件；部署正文、hooks调查及历史重组不占地图正文 |
| `ops/agents/`、`ops/docs-governance.md`、`.codebuddy/work/README.md` | 统一流程、生命周期、历史读取触发，减少多处重述和强制记录动作 |
| `ops/前端设计守则-以使用用户为中心.md`、D29 | 留有效界面与用词要求；已撤功能和改动流水不再默认读取 |
| 主计划、architecture/modules/deployment 等主人 | 保持当前职责；核对迁移后残留的旧要求和反向指针，不重做前轮瘦身 |
| 仓外《说明书》、PRD/MOD-*、验收资料及原型引用 | 查明现行规则、程序现状和历史原型各自用途，避免已退场需求仍支配日常改动 |

具体做法：

- 当前步骤放前面，参考按任务分支披露；给每个入口明确“什么情况下读”，不要求整册顺序通读。
- 对代码/配置一次查询就能得到的事实，优先指向其主人；只保留查询不易发现的约定、边界与必要理由。
- 历史默认不读。只有复发排障、当前约束含义无法确认或明确追溯决定时，才沿指定证据读取，并说明原因。
- 删除或归档只保护旧形式的内容时，同批处理活引用和对应守卫。Git 可恢复的过程不要求另复制全文或新增长归档索引。
- 仓外有效业务要求和验收含义不擅自改变；可按本规格整理过程/陈旧副本与结构。遇到实质业务冲突先报告，待确认后更新唯一主人。
- 不把本规格加进日常必读入口。实施后，稳定规则进入其主人，本规格退出日常路径。

完成标准：常读入口不存在未解决的互相矛盾指令；每项现行含义只有一个主人；历史不因普通小改被默认读入。未能解决的冲突逐项明确列出。

### 阶段三：审查检查与守卫

从现有入口及阶段一实测触发的检查出发，避免为盘点而逐支运行全仓测试。

| 检查性质 | 处置方向 |
|---|---|
| 当前业务结果、金额、写入、权限、迁移和恢复保护 | 核实真实后果及覆盖，按影响执行；不因耗时撤掉 |
| 检查选择、漏验防护、失败失效、结果可信性 | 保留有现行用途的保护；机制变更时跑对应自证，普通业务修改不重复全套元测试 |
| 文档形式、重复计数、旧原型字面、历史叙事和已退场需求 | 证明无现行用途后，连同规则、测试及引用一起退出；有用但无须阻挡交付的提示可降为按需检查 |

每项处置只需说清：保护什么、当前是否仍需要、触发条件、成本、动作及失去什么。记录在执行票或改动说明，不新建永久双份清单。

既有修改不能被冒充为已验，但也不能仅因未提交而反复全验。需区分本轮新增影响、未变化且有效的验证结果、实际会影响当前任务的未验输入。复用机制沿用/简化现有实现，不另造多层缓存和证明平台。

完成标准：没有仅凭旧需求或旧形式阻挡当前交付的检查；长检查的触发理由可解释。删除检查要有其保护目标已退场/被替代的证据，不能只报速度变快。

## 5. 验收场景

| 场景 | 应读与应验 | 失败判据 |
|---|---|---|
| 新 agent 干净上下文接手 | 当前入口、最新状态/交接及当前任务主人 | 为普通接手回读日志、归档或整册事故；遗漏/冲突导致重复讨论已确认需求 |
| 普通说明、索引或过程文字小改 | 受影响内容、必要引用/结构，机器消费时补对应使用者检查 | 无业务影响却触发全套业务 pytest、全部变异或仓外整体验收 |
| 局部功能小改 | 相关业务规则、直接共享影响、对应回归 | 无关旧 dirty、治理黄档或提交动作扩大到全仓；相关业务风险反而漏验 |
| 金额/权限/批量写入/共享机制改动 | 查明触达范围，验证真实后果，必要时扩大 | 按“局部文件”误判低风险；没跑相关保护却报告通过 |

补充反例覆盖：新增普通说明文件、修改真实机器输入、保留既有 dirty、检查失败后复跑、文档与代码冲突。只运行证明本轮新选择规则所需的反例，不把验收做成又一套每轮必跑流程。

每个场景报告实际读入的主要文件/章节和理由、运行/跳过检查及依据、各长检查与总耗时、未验风险。验收不设统一分钟限额，也不以文件/测试数量下降代替准确性。

## 6. 汇报、收尾与例外

开工简述相关资料范围；读取历史或扩大核验前说明触发原因。收尾报告实际依据、修改范围、检查结果/耗时和未达成项，不逐条播报读文件、不另写永久阅读日志。

不再要求每次小改生成长日报、全文备份、逐次销号叙事或事故复述。记录够支持当前目标、验收和下一次接手即可；稳定约束回其主人。

发现无关故障先区分是否影响本轮结论。相关检查失败不能报通过；复跑通过不冒充一次统一全绿。只重跑受失败/修补影响的检查，不把某支自证复原失败当作重跑所有业务测试的理由。

整改本身不改业务功能、不抹去未解决风险，不修改/提交凭据。原有未提交修改保留，工作文件临时变异残留必须按已保存字节恢复。
