## 一、从付款通知书页读到的三条倾向

### 1.1 操作习惯

| 观察到的行为 | 你实际表达过的话 | 反推出的习惯 |
|---|---|---|
| 逐行「付款」按钮被砍，改成勾选 + 一次批量付款 | 「付款按钮太大了…放别的地方」 | **批量优先**：不要逐行操作，要"勾选 → 一次动作" |
| 改分类从 4 步（勾选→按钮→弹窗→确认）压到 1 步 | 「点击次数太多了，重新设计」 | **少点击**：能一次做完就绝不两次 |
| 原生年月控件被要求重做 | 「滚轮滑着太慢」 | **拒绝笨控件**：不为"系统自带"买单 |
| 筛选不要「应用」按钮 | 「去掉这个按钮，保留 data-act」 | **即时生效**：中间确认是负担 |
| 勾选后要看到行数与两个金额 | 「这几个位置正好可以改成已勾选审批金额和已勾选付款金额」 | **决策要看到量**：动作前必须知道影响多少 |
| 关键数值要能改 | 「付款金额要能手动改」 | **人工可覆盖系统值**，但改动必须可见 |
| 默认值必须合业务 | 「默认改成未付清」「项目都应该是在建」 | **默认要贴合日常**：打开即是对的场景 |
| 临时改动不要留痕到永久 | 「保留到页面刷新然后就恢复默认」 | **临时与持久要分清** |

### 1.2 交互方式

- **不要多余的确认**：批量改分类删掉了二次确认弹窗。
- **拦截要讲原因**：每处拦截都给出"为什么 + 原值已保留"，不是干巴巴报错。
- **弹层要能自己消失**：点外部 / Esc 都能收起。
- **异常状态要显性**：只读、可改、已改，三种状态视觉上必须一眼可分。
- **边界要有交代**：空结果、部分选中、超额输入，都要有明确反馈。

### 1.3 审美偏好

> ⚠️ **本节的定性（2026-09-13 用户澄清）** —— 用户原话：「**对于 UI，我只希望交互我用着舒服，外观审美完全看你发挥，有高级感一点就行**」。
> ⇒ **外观审美（配色 / 密度 / 层级 / 留白 / 元件尺寸）交由实现方发挥，评判标准只有一条：有高级感**；本节只保留**与"用起来"直接相关**的几条。
> 🚫 **已作废（勿用）**：原「**操作区要密 · 拒绝大色块大按钮**」与「**一屏只留一个主动作**」两条 —— 它们是**从个别反馈外推出来的**，**用户从未表达过**（2026-09-13 用户：「我没有任何印象，肯定是 AI 过度理解我的意思去加的」）。**不得据此限制按钮数量、元件尺寸或版面密度。**

- **大卡片保留**：域级总览的指标卡**好看、有高级感**，继续用。
- **对齐即专业**：金额右对齐 + 等宽数字，小数点对齐。
- **颜色只承担语义**：不做装饰性用色。
- **口径写在字段旁边**：用列头灰色小字，而不是堆一大段提示。

## 二、可复用设计规则（R1–R19）

> 每条规则都标注它在付款通知书页的**对应依据**。

### R1 · 页首说明：一个可折叠块

| 项 | 内容 |
|---|---|
| **规则** | 每个页面的口径说明合并为**一个** `<details class="tip">`，默认收起；`summary` 统一为「**口径说明 · N 条**」+ 灰色引导语；正文用 `<ul>` 条目化 |
| **依据** | 付款通知书页原先几段彩色提示条堆成"文字墙"，后合并为一个折叠块 + 条目列表（**条数以原型为准**，见 `MOD-03` 的「口径说明」） |
| **例外** | **整页即说明**的页面不折叠（`MOD-10` 机械费暂缓页）；**单行短说明**不折叠（看板的**页首说明**）；**卡片内的就近说明**保持展开（如"列结构说明""待确认 OPEN-xx"）<br>⚠️ **2026-09-14 补充**：看板「页首说明」仍是单行、**不折叠**；但该页**页内新增了一处折叠**（`<details class="tip">` 包住「状态机汇总（§8.3）」规则表，为把首屏让给待办）⇒ 看板**不再是"整页零折叠"的页**。**机器白名单 `DETAIL_EXPAND_OK` 里的 `home` 已移除** —— ⚠️ 这不是放宽：移出后 **R1 第 1 条反而开始要求看板有折叠块**（把"白名单"改准，见 §五 对应断言） |

### R2 · 指标区：**两种形态并存，各管一段**

| 形态 | 用在哪 | 形态特征 | 依据 |
|---|---|---|---|
| **大卡片 `.kpis`** | **域级总览** —— 看板、`MOD-04`、`MOD-05`、`MOD-11` | 卡片式，字大、留白足、带副标签说明口径。**好看、有高级感，保留** | 用户明确表示大卡片好看 |
| **汇总条 `.selbar`** | **操作上下文** | 一行 50px，「label 11px 灰在上 / 值 14.5px 等宽在下」+ 竖分隔线 + 右侧操作位，吸顶 | 由付款通知书页把 4 张欠款卡 + 大按钮合并为一条而来 |

**判断口径：** 这个指标是"**看全局用的**"（≥4 项、需要解释口径、不承载动作）→ 大卡片；是"**做动作前看影响用的**"（跟随选择变化、旁边紧跟主操作）→ 汇总条。

### R3 · 主操作的位置与样式

| 项 | 内容 |
|---|---|
| **规则** | ① 列表页的**主操作**放在**汇总条右侧**或**卡片标题栏右侧**；② **行内操作**一律用 `.btn.sm`；③ **一页允许出现多个主按钮** —— 要求不是"数量"，而是**每个主按钮都指向一件明确的事**。 |
| **「导出 Excel」是列表页的主操作之一** | 领导要 Excel（《说明书》§7.1：所有列表页都要「导出 Excel」）⇒ 它**保持主按钮样式**（2026-09-13 用户裁定「走乙」）。 |
| **依据** | 付款通知书页：主操作=「付款」；行内只剩"改分类"这类小动作，且改成了下拉（无按钮） |
| 🚫 **已作废（勿用）** | 「**每页只允许一个 `.btn.pri`**」—— 该条是从一条**未经用户确认的"偏好"**外推出来的；用户 2026-09-13 澄清**对主按钮数量没有要求**。**不得据此把「导出」降级，也不得给页面强加"只能有一个蓝按钮"**。 |

### R4 · 筛选栏 `.fbar`

| 项 | 内容 |
|---|---|
| **规则** | 列表页筛选统一用 `.fbar`：**label 在上（10.5px 灰）、控件在下**；**改动即时生效**（不设「应用」按钮）；右侧 `.pill` 显示**命中计数**；提供「重置」。<br>**适用范围**：统一于**列表页**（**具体页面集合以原型与自检基线为准**，本文不列举）。<br>**例外**：**`MOD-06` 过程资料**的筛选栏**不设「重置」**（该页筛选只有「选项目」一项 + 计数；项目选择**复用共用的项目面板但为单选**；**核算月不作筛选控件** —— 它只作表内列） |
| **依据** | 付款通知书页的筛选栏；其中「申请筛选」按钮被明确要求**删除**，改为即时生效 |

### R5 · 弹出层三条硬要求

| 项 | 内容 |
|---|---|
| **规则** | ① **宽度内容自适应**（`width:max-content` + min/max 钳制）——不留大片空白、也不截断文字；② **点外部 / Esc 自动收起**；③ 内部文字**不做省略号截断**；④ **面板类弹层**（如项目多选）提供**「全选 / 清空」**快捷项 |
| **适用范围** | 本规则只管**仍然存在的弹出层**（弹窗 **+ 浮层面板**）。⚠️ **2026-09-13 增行模式取消了 3 个「新增」弹窗** ⇒ 那 3 处**不再受 R5 约束**；但 **R5 本身不废** —— 其余弹窗（删除确认 / 批量付款 / 关联集采合同 / 抓取 / 付款计划导入 / 三个子表 / 用户管理 / 活动大表选题 / 剔除规则 / 归属判定 …）与**全部浮层面板**（各页「项目」面板 · 年月面板）照旧受约束 |
| **增行展开区（2026-09-13）** | 「展开区」**不是弹出层** ⇒ 不受①②④约束；但**③（文字不做省略号截断）照旧适用**，且补一条：**`Esc` / 点外部要能收起**（展开区里的浮层面板仍走"点外收起 / Esc"那套登记） |
| **依据** | 项目多选面板被反馈"太宽、留空白、把项目名挡住"三次；固定宽度是根因 |

### R6 · 年月选择统一用一个组件

| 项 | 内容 |
|---|---|
| **规则** | 凡需"选时间"处一律用 `tmBtn()` 通用时间选择器：按钮 → 弹出面板，**最多两次点击**；含「本月（北京时间）」快捷项。**能力由调用点声明**（`modes`：月 · 跨月 · 年 · 季度 · 周 · 全部），**组件内不按 scope 分支** |
| **依据** | 付款通知书页的原生 `input[type=month]` 被反馈"滚轮滑着太慢"后自研 |
| **⚠️ 不设「全局核算期」** | 顶栏那个控件已删；各表**各自**取默认年月，统一走 `bjMonth(偏移)`。**用户可改**、抓取与筛选范围以界面所选年月为准 —— **取值口径以《说明书》§9.2「各表默认年月」为准，本节不复述** |

### R7 · 表格

| 项 | 内容 |
|---|---|
| **规则** | ① `.tw` **必须有高度上限**（否则 sticky 表头会跟着滚走）；② 数字列右对齐 + 等宽字体；③ **列头用灰色小字补口径**（如「审批金额（只读）」「付款金额（本次应付 · 自动）✎」）；④ 可手改列标 `✎`；⑤ ⭐ **「合计」行统一置底**（2026-09-13 用户口径）—— 表头贴顶、合计行贴底，数据量大时**不用滚到底才看得到**；`sumRowOf` 产出的行带 `sumrow` 类，由样式表实现（**`position:sticky;bottom:0`** ＋ **不透明底色** —— 吸附行**必须有不透明底色**，否则数据行会透出来；`border-collapse:collapse` 下边框会丢 ⇒ 用 `box-shadow` 补）。<br>⭐⭐ **实现这一条最容易踩的坑（⚠️ 历史原型曾使用错误写法）：`position:sticky` 必须落在 `<tr>`（或 `<tfoot>`）上 —— 写在 `<td>` 上永不生效。** 根因：`sticky` 作用在 `<td>` 时**包含块是表格行**（行高 = 单元格高）⇒ **没有可位移的空间**。实测（真实浏览器，容器高 200px、表内 30 行）：`td` 写法「合计行底 − 容器底 = **+792.5px**」（合计行在屏幕外，**必须滚到底才看得见**）vs `tr` 写法「**−1px**」（吸附生效）。⚠️ **它不报错、不崩、只是不生效** ⇒ 只能靠**实测**抓出来。<br>⚠️ **原型 已退役原型 里「合计行由 `sumrow` 钉在表尾」那条注释与实测不符** —— 该规则**从未生效过**；只是"数据序置底"成立，让人误以为"视口吸附"也做了。<br>⚠️ **关掉吸附 ≠ 关掉置底**：传 `sticky:false` 时合计行**仍钉在表尾、仍不参与排序**。⚠️ **分组表例外**：分组合计要紧贴本组（`MOD-07` 焊材/气体提取传 `sticky:false`），两行同 sticky 会重叠 |
| **依据** | "往下拖表头没了"的修复；列头副标题是付款通知书页解释口径的主要手段；置底的由来 = 用户提出"库存单据这种数据量大的，合计要拖到最下面才看得到" |

### R13 · 表头点击排序（数据列表）

| 项 | 内容 |
|---|---|
| **规则** | **数据列表**的表头可点击排序。**三态循环：升序 → 降序 → 原序**，可反复切换；**同一时刻只有一列生效**（点新列即从该列升序开始） |
| **指示器** | **当前排序列**：常显 **▲ / ▼** + 主色；**其余可排序列**：淡灰 **↕**，表头悬停时变深。未排序时表头不出现任何强调 |
| **不参与排序的列** | **动作列**（表头为「操作」「处理」）、**复选框列**、**空表头列** —— 点了无反应、也不显示指示器 |
| **钉住行** | 含「**合计 / 总计 / 小计**」的行、跨列提示行（空态）**恒在最底**，不参与排序 |
| **类型自动识别** | **数字**（金额 / 数量，忽略千分位与 ¥ %）、**日期**、**中文文本**（按拼音）。**空值恒排最后**，不随升降序翻转 |
| **排序只重排行** | **不改写任何单元格内容** —— 尤其不动行号 / 编号类字段 |
| **适用范围** | 只给**数据列表**加（页内 + 弹窗内）。**不加的三类**：**说明表 / 规则表 / 打印表** —— 例：`MOD-02` 接口清单、`MOD-14` 规则表、`MOD-06` 过程资料的「原始 / 调整后」表与「差异」表（打印/上报表）。行数少或属打印件，排序无意义，加了反而让人以为"这能排" |
| **弹窗内的表** | 与页内表**完全同款**（三态 / 指示器 / 不可排列一致）；排序后**弹窗就地重绘**，已填的表单值**不丢** |

### R17 · 「自动预填 · 待确认」态（系统代填的值必须过一道人工闸）

| 项 | 内容 |
|---|---|
| **规则** | 系统**自动算出一个值并代填**时，**一律不静默落库**：值**先写进待确认态**（视觉 = `.ed` 黄底输入框 + 「**自动匹配 · 待确认**」橙标签），并就近给**两个出口** —— 「**采用**」（确认后转正式值、标签消失）／「**不采用**」（清空值、回到手工）。**人工直接改一次**同样视为确认（标签随之消失）。 |

| **适用范围** | `MOD-03` 「集采实际供应商」列。⚠️ **本规则是通用形态**（凡"机器代填 + 人工必须过目"的字段都可套），但**当前只有这一处实例**。 |

### R19 · 再次导入的合并与提醒（源字段跟随 · 旁路"未改跟随 / 手改保留" · 越界只提醒不代改，`2026-09-14`）

| 项 | 内容 |
|---|---|
| **前提（必须先讲清）** | §4.2.5 那句「**审批金额 ✗ 不被覆盖**」的意思是 **"不被人工编辑覆盖"**，**不是** "不被 i8 覆盖"。⇒ i8 侧**改了单据**再导一次时，**审批金额是会跟着 i8 变的**（它是**源字段**）。真正的风险**不在源字段本身**，而在**由它派生的旁路**： |
| **合并规则（逐字段）** | ① **源字段**（**审批金额 `approve`** / 项目 / 分类 / 单据名…）**一律跟随 i8 的新值**；<br>　　ℹ️ **2026-09-16**：源字段由**两个减为一个** —— 原「**付款金额（源）**」（`pay`）**已取消**（i8 申请金额与审批金额**实测恒等**、且**付款动作不在 i8 发生** ⇒ 零信息量、零消费点）。原型 `NT_COLS` 里的 `pay` **保留不删**（**界面上从不显示、不参与任何口径**，仅为演示数据位置兼容）⇒ **不必据此实现**；<br>② **旁路字段**（`统计结算金额` `ss` / `统计付款金额` `sp`，= 人工可覆盖的派生值）**按"有没有被人手改过"分叉**：<br>　· **没手改过** ⇒ **跟随新值**（`n.ss = n.sp = 新审批金额`）；<br>　· **手改过** ⇒ **保留人工值 + 挂提醒**（**绝不自动改写人的值**）。 |
| **判据 = 留痕，不是新状态位** | "这行有没有被人手改过" **唯一的判据是留痕**（`hasT(n,'统计结算金额')` / `hasT(n,'统计付款金额')`）。⚠️ **两个字段各自判**（有人只改了 `sp` 没改 `ss` ⇒ 只保 `sp`）；⚠️ **不新增"已确认"之类的状态字段** —— 那会变成"同一事实两处存"。 |
| **越界处理：只提醒、不代改** | 若 i8 **把审批金额调低**、而人工值**仍然高于新上限**（`overCap`）⇒ **不改人的值**，只在**该行「审批金额」单元格挂一个「导入提醒」标签**（`IMP_WARN`，悬停列出哪几个字段越界、越界多少）。**为什么不自动改**：① 人的值可能是**先算好的正确值**、i8 才对不上；② 自动改 = **静默改人的数据**（最贵的失败模式）；③ 上限的**铁律只在"人编辑的那一刻"拦截**，**拦不住"上限自己掉下来"** ⇒ 只能**事后提醒**。 |
| **值没变就不动（防伪重算）** | 合并**只在 `新审批金额 ≠ 旧审批金额` 时**才做（`impMerge` 的第一道闸）。⇒ 同一份 i8 数据**再导一次（值没变）不会触发任何提醒、也不会把"已手改"标记弄乱**（否则每次导入都刷一堆假提醒）。 |
| **i8 已撤单 / 已删除的单据** | 导入时 i8 侧**已不存在的单** ⇒ **不硬删本系统里的记录**，改为标「**i8 已撤单**」（`IMP_GONE`，判据 `ntVoid`），**保留可查 + 退出全部统计 + 默认隐藏**。**理由**：① 若退出统计而不留行，**已挂的付款流水 / 集采关联会变悬空引用**（比"多一行"更难查）；② i8 行是**源数据**，本系统**不得单方面抹掉**（§9.3）。<br>⭐ **退出统计的唯一出口 = `ntLive(n)`**（= 未剔除 **且** 未撤单）：**凡"参与统计 / 参与合计 / 参与欠款 / 参与候选"的出口都走它**；凡"看剔除记录"的视图出口**保持 `excl`**（那一档还要承载撤单行）。<br>⭐ **有牵涉 ⇒ 硬拦**（`ntVoidJoint` = 该行**已挂生效付款流水或集采关联**）：**不许静默退出统计** —— 行**仍算有效**（继续参与统计）、**留在列表 + 带警示**，提示「**请先撤销付款 / 解绑关联**」；处理完（流水撤销 / 关联解开）它才自然退场。<br>⭐ **撤单标记 = 终态**：i8 删了再建 ⇒ **单据号必变** ⇒ **不做"下次抓回来自动复原同一行"**。<br>⛔ **不提供「删除付款通知书」按钮**：排除撤单靠「**退出统计**」而非"删除"（i8 行永不删、源数据只读）。<br>⚠️ **藏处 = 并进现有「分类 = 剔除」视图**（按**来源分档**：剔除行显「剔除」、撤单行显「i8 已撤单」，**不相混**），**不新增分类枚举值**（`ENUMS.cat` 值域不变）。 |

## 四、本规则的边界（明确不覆盖 · **只约束 `R1`–`R12`**）

> ⚠️ **适用范围**：本节只约束 `R1`–`R12`（表现层）。`R13`–`R19` 是**后续新增的交互能力**，它们**会**规定按钮可用条件、排序行为、带入态、归属入口、**自动预填的确认态**、**操作列的处置出口**、**再次导入的合并与提醒**等 —— **不受本节约束**。

| 项 | 原因 |
|---|---|
| **不动任何金额计算、状态判定、校验规则、勾选逻辑** | 属核心业务逻辑 |
| **不动任何按钮的可用条件、字段的只读性、数据的存储语义** | 属功能定义 |
| **不做列宽拖动** | 已明确决定不做；如需做，必须先切换 `table-layout: fixed` |
| **不统一表格列宽** | 各页列数与语义差异大，强行统一会牺牲信息密度 |

### 8.3 五条准则

| # | 准则 |

| 1 | **同一个事实只写一处**：值域 · 规则 · 列结构 · 候选构造 —— 都只允许一个出口 |

### 8.4 可改字段的「非法输入」判据差异（**有意保留，别"顺手统一"**）

> **取值与判据的主人 = 《说明书》§8.4「口径一致性清单」的「可改金额字段的取值判据」一行** —— 本节**不复述取值**（三档分别拦什么，去那一行看）。
