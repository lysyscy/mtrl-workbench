## 0. 结论速读（先看这一段）

| 层 | 推荐 | 一句话理由 |
|---|---|---|
| 语言 | **Python 3.13**（本机实况；原 3.12 为建议值） | Excel（openpyxl/pandas）与 i8 纯 HTTP 抓取生态最成熟；`Decimal` 金额口径原生支持（§9.1） |

| ORM / 迁移 | **SQLAlchemy 2.0 + Alembic** | 事务内取号、UPSERT 幂等、软删留痕（⚠️ §9.4 **2026-09-20 定案**后该档**只落在「账号」**）均需 ORM 事务能力（§9.5、§9.4） |
| 数据库 | **PostgreSQL 16（同机本地服务）** —— ⚠️ **2026-09-15 变更**（原为 SQLite，见 §3.0） | `OPEN-T1`（局域网一台机器、仅后端进程访问库）下：**`SELECT … FOR UPDATE` 行锁**支撑付款「读余额→校验→写流水→重算」临界区（**SQLite 无行锁**）· 原生 `numeric(18,2)` 精确小数 · MVCC 并发；**本机 PG 16 早已装且在运行**（服务 `postgresql-x64-16` · 本机 PgSQL 目录）⇒ `OPEN-T8`「少组件」的运维增量**已经付过**；量级 <30 万行/表（§2.9）对两者均无压力。⚠️ **本条原附的"某工程实测"依据已删** —— 证据随该工程被删除而消失（2026-09-15 复核）；判定改按**文档一致性 ＋ 技术等价性** |

| i8 接入 | **httpx**（Cookie 会话 + 过期自动重登） | 纯 HTTP 登录态与 `API-05/06` 抓取（§3.1.2） |
| 打印 / PDF | **本地渲染 PDF（Python 无头浏览器）→ IPP 直投打印机**；常规报表出纸走「按模板导出 → Excel 打印」 | 付款通知书批量打印 = **系统内建 · 版式取自 i8**（§4.6 `DEV-P-07`）；**A3 打印已于 2026-09-14 整条取消** |

## 2. 候选方案对比

> 每类给出 2–4 个候选。**「硬约束」栏逐条标注是否满足**，重点标注：① i8 不可用时的 Excel 降级；② 打印出纸（付款通知书 / 常规报表）；③ 中文路径 / GBK；④ 事务内取号；⑤ 幂等导入；⑥ 手动行不被覆盖。图例：✅ 满足 ｜ ⚠️ 需额外处理 ｜ ❌ 不满足。

### 2.1 C1 · Web 后端框架（先定语言：Python）

| 候选 | 优点 | 缺点 | 关键硬约束 |
|---|---|---|---|
| **Python + FastAPI** | 生态贴 Excel/HTTP 抓取；Pydantic v2 强校验（贴 `DEV-*` 枚举）；自动 OpenAPI（利于交接）；异步利于 i8 抓取 | 异步与同步 Excel 需线程池隔离；无内置后台/权限 | Excel 降级 ✅ / A3 ✅（浏览器侧）/ GBK ✅（可 `encoding` 指定）/ 事务取号 ✅（ORM）/ 幂等 ✅（ORM 事务）/ 手动行不动 ✅（建模层可控） |
| **Python + Django** | 全栈齐备：ORM+迁移+Auth+Admin（`MOD-14` 配置表 + 2 账号管理近乎免费，§1.5.1）；模板+HTMX 可零 Node 构建 | 偏重；SPA 需 DRF；异步弱 | 同上 **全 ✅**（且 Admin 白送） |
| **Python + Flask** | 极轻、灵活，Jinja + SQLAlchemy 组合简单 | 需自行拼装校验/迁移/权限；无 OpenAPI | 同上 **全 ✅**（代码量略多） |
| **Node + Express** | 前后端同语言（若前端 React/Vue）；i8 HTTP 方便 | **Excel 生态弱于 Python**（ExcelJS 不如 openpyxl/pandas）；`Decimal` 依赖库（decimal.js）非原生；`numeric(18,2)` 需 ORM 支持 | Excel 降级 ⚠️ / 事务取号 ✅ / 幂等 ✅ / 金额 ⚠️ |
| **C# + .NET** | Windows 原生、服务化/Excel（ClosedXML/EPPlus）成熟、强类型 | 学习/交接面窄；i8 抓取生态一般；跨语言协作成本 | Excel ✅ / A3 ⚠️（LibreOffice）/ GBK ✅（需显式 `Encoding`）/ 事务取号 ✅（EF Core） |

**小结：** 语言层 **Python 胜出**——Excel（C3）是重头戏，且 `Decimal`/`numeric(18,2)`（§9.1）与 i8 纯 HTTP（C5）在 Python 最顺；框架层 **FastAPI 为主选**（REST+校验+SPA），**Django 为「少写代码」备选**（Admin/Auth/迁移免费），**Flask 为极简备选**。**不选 Node**（Excel 与 Decimal 吃亏），**不选 C#**（生态与交接面窄）。

### 2.3 C3 · Excel 读写与模板

| 候选 | 优点 | 缺点 | 硬约束覆盖 |
|---|---|---|---|
| **openpyxl** | 开箱读写 `.xlsx`；样式/列宽/公式/多 sheet；**过程资料 17 列模板、集采台账 Excel 风格、列表导出** 全覆盖；可 `openpyxl` 直接写公式 | **不能求值公式**；`原表数据透视表`（§5.3.2）原生支持弱，需变通 | 模板导出 ✅ / 风格 ✅ / zip ✅（配合 `zipfile`）/ 透视 ⚠️ |
| **pandas（+ openpyxl 引擎）** | 读付款计划、分组透视、焊材/气体提取（§5.3.3）最省力；数据分析强 | 写「带样式的模板」不如 openpyxl；大表内存占用 | 读取/透视 ✅ / 样式 ⚠️ |
| **xlsxwriter** | 写出高保真、性能好、图表/条件格式强 | 只写不读；透视表同样受限 | 写 ✅ / 读 ❌ |
| **商业库（Aspose.Cells / Spire.XLS）** | 保真与透视表/公式求值最强 | **收费、授权、体积**；与「内网小工具」性价比不符 | 透视为数不多的解 ✅ 但成本高 |

**小结：** **主选 openpyxl（写模板/导出）+ pandas（读入/透视/提取）组合**，二者同属 Python 生态、可互操作；`zipfile` 打包分仓库结果（§5.3.2）。**`原表数据透视表` 列为风险点**（见 §5 风险）：Plan B = 用含「已建好透视表的数据表模板」注入数据，或把透视结果以数值形式输出。**不选商业库**（成本不匹配）。

**① 决定裁决的三个事实**

| # | 事实 | 出处 |
|---|---|---|
| a | 「局域网一台机器」= **一个后端进程承载业务、2 人经浏览器访问该机地址**；数据库**只被该后端进程访问**，**不是「SQLite over SMB」** | `OPEN-T1` 语义 |
| b | 文档对「事务内取号」**明确给出两种等价实现**：`SELECT MAX` + 行锁 **或** 唯一索引 + 重试；⚠️ **但该条只覆盖「取号」，未覆盖付款临界区** —— 付款「读余额→防超付→写流水→重算」必须行锁 | 《实施计划》§四·技术项 5 |

| 维度 | 结论 |
|---|---|
| 组件数 | **1 个同机 DB 服务** —— ⚠️ **本机早已装且正在运行**（`postgresql-x64-16` · `Auto` 启动）⇒ 相对 T8「少组件」的增量**已经付过**，不构成新增运维面 |
| 备份 | **`pg_dump` + 计划任务 + 副本保留策略**，对应 `OPEN-T2`（原"单文件在线备份"随之改） |

**③ 关于「用户本人维护」的负担对比 —— ⚠️ 2026-09-15 结论反转**

- **现结论（选 PostgreSQL）**：PG 那笔「额外装 Windows 服务（占端口、设口令、随版本升级、写 `pg_dump` 备份脚本、故障排查）」的**长期运维面，在本机已经存在**（`postgresql-x64-16` 早已装且在跑）⇒ 它不是"新增成本"，而是"**既有事实**"。而 T1 单机场景下，PG 的**行锁优势恰恰是本项目真要用的**（付款临界区）。
- **选 PG 后的降负担做法（沿用既有实践）**：绑定本机回环端口、口令写入服务配置、备份用计划任务 `pg_dump`、禁止外部访问；**服务账户沿用"专用本地账户"做法**（老工程用 `.\svc_caibao`，**非 LocalSystem**）。
- **若将来需回切 SQLite**：触发条件见下方 **④（已反转为"回切条件"）**。

**④ 数据库回切触发条件（⚠️ 原为「切 PostgreSQL 的触发条件」；2026-09-15 已完成切换 ⇒ 本条反转为「回切 SQLite 的条件」，任一命中才考虑回切）**

| # | 回切触发条件 | 说明 |
|---|---|---|
| 1 | PG 服务在目标机器上**不可安装 / 不可长期运行**（运维方变更、环境策略限制） | 前提反转 |
| 2 | PG 的**运维负担实际压垮用户本人**（备份失败、版本升级、故障反复） | T8 诉求重新占上风 |
| 3 | 交付形态变为**「单文件绿色版」**（拷走即用、无需装服务） | 单文件分发是 SQLite 独有优势 |
| 4 | 数据量**长期停在极小规模**且并发写入者始终 = 1 | PG 的行锁价值无从发挥 |
| 5 | 需**把库随交付物一起打包外发**（审计 / 复盘副本） | 单文件更便 |

> **回切成本可控 —— 但有两处不可自动迁移**：SQLAlchemy 抽象 + Alembic 迁移使 **PostgreSQL → SQLite 为「换连接串 + 跑迁移」**；⚠️ 但 ① **付款临界区的行锁**（`SELECT … FOR UPDATE`）在 SQLite 上**不存在** ⇒ 需改设计；② 金额口径以本文 §3.2 为准。因此**回切不是纯工程动作，须重新评估**。

| 维度 | 原结论（SQLite，已失效） |
|---|---|
| 组件数 | 无独立 DB 服务（PG/MySQL 需装并长期维护服务、端口、账号、升级）→ 直接满足 T8「少组件」 |

## 8. 接手开发须知（本机环境坑）

> **定位：** 本节讲的是**开发这台机器上的工具坑**，不是业务事实、也不是选型结论；**换机器后请重新核实**。维护方 = 接手开发者。
> **出处：** 原为《说明书》§0.3，2026-09-12 **下沉至此**（业务文档只留一行指针）—— 理由：与业务无关，放在"业务唯一权威"里会被业务读者误读。

| 现象 | 应对 |
|---|---|
| **Bash 命令前必须补 PATH**（PortableGit shim 缺 coreutils：`ls` / `tail` / `dirname` / `rm` 全无 ⇒ 报 `command not found`） | **Bash 工具可用**，只需前置 `export PATH="/usr/bin:/bin:/c/Windows/System32:$PATH"`；**判文件是否存在用 Glob**，不要靠 `ls` 的报错推断 |
| **PowerShell 工具不回显 stdout** | 结果**落盘再用 Read**、读完删；写盘用 `[IO.File]::WriteAllText($p,$txt,(New-Object Text.UTF8Encoding($false)))`（`1>file` / `*>` 会写 UTF-16LE） |
| **输出是 GBK，中文会乱码** | 先设 `[Console]::OutputEncoding = New-Object Text.UTF8Encoding($false)`，再落盘 |
| **Glob / Grep 在中文路径下可能失灵** | 目录清单用 `Get-ChildItem` 落盘核对，勿凭想象下结论 |
| 中文编码坑 | 子进程 stdout 用 `errors='replace'`；`Get-Content` 必须带 `-Encoding UTF8` |
| 文件删除 hook | 多路径单次删除会整体失败 → 逐项 `[IO.File]::Delete()`；新方法先用无关目标验证 |
| 沙箱内 git 远端操作必然失败 | push / fetch 只能由用户终端执行 |

### 9.2 `API-01` 付款通知书列表 —— ⚠️ **POST 表单，不是 GET**

- **URL / 方法**：`POST {BASE}/FC/FM/PaymentBill/getList`，`Content-Type: application/x-www-form-urlencoded`。
- **固定表单**（缺项会取不到数）：

  | 键 | 值 |
  |---|---|
  | `busType` | `PaymentBill` |
  | `pageId` | `Web:PaymentBill` |
  | `isLoadHistory` | `1` |
  | `relateId` | `14` |
  | `inputSource` | `2` |
  | `phidOrgList` | `3700000000000014` |
  | `phidProjList` | `""`（空串） |
  | ⭐ **`dataKey`** | **必须传空串**（照抄素材包实现时的常见漏项） |
  | `saveTableName` | `fc3_code_table` |
  | `payStatus` | `0` |
  | `summaryCols` | `ApplyAmtFc,ApplyAmt,ApproveAmtFc,ApproveAmt` |
  | `limit` / `page` / `start` | `5000` / `0` / `0`（单张精确查用 `limit=5`） |
  | `queryfilter` | **双层 JSON 串**：`{"queryFilter":"{\"BillDt*date*ge*1\":\"YYYY-MM-DD\",\"BillDt*date*lt*1\":\"…\"}"}` |

- ⭐ **月份 → 入参**：按月抓 = **换算成「单据日期」闭区间**；**不要**试图传 `yearMonth` 之类（**实测一条也取不到** —— 这是旧实现踩过的坑）。
- ⭐ **单张精确查**（性能硬规则）：`queryfilter` 用 `PhId*guid*eq*1`（15 位以上纯数字）或 `BillNo*string*eq*1`；**绝不走全量列表**（实测：全量 1064 条 **44.9s** vs 精确 1 条 **0.16–0.33s** ⇒ 快约 **138 倍**）。
- ⚠️⭐ **空结果必须再确认一次**：i8 会**偶发返回"有效但空"**（并发时更明显）—— 空 = "单据不存在"，**不确认就会少出一张单**。同理 **流程接口回空 ⇒ 所有签名静默漏印**，也必须确认一次。
- **响应**：`{"Record": [ ... ]}`（分页字段同在顶层）。
- ⚠️ 响应字段**远多于**导出表需要的 12 个（还含 `PhidApp_EXName` / `ApplyAmt` / `PrintCount` / `NgRecordVer` …）⇒ 12 个是**导出表**口径，取数按需取。
- ℹ️ ⭐ **本工程不取 `ApplyAmt`**（2026-09-16）：原「付款金额（源）」字段**已取消**（§4.2.5）；金额只取 **`ApproveAmt`（审批金额）**。实测 `ApplyAmt ≡ ApproveAmt`，且**付款动作不在 i8 发生**（在会计 NC 系统）⇒ 该字段**零信息量**；「已付金额」= **付款流水汇总**（本系统内产生 / 由历史 Excel 导入）。

### 9.5 `API-07` 取版式 —— ⭐ **拿到的是"版式模板 JSON"，不是 HTML**

- **URL**：`GET {BASE}/reportcenter/printManage/getPrintDesign?printId=<printId>`。
  ⚠️ 另有同族的 `RW/Print/GetPrintTemplate` —— **号段不同、会撞号拿到不相干的单据模板**，别混用。
- **响应外层** = `{"Status","Code","Msg","Data"}` ⇒ **模板在 `Data` 里**（不是顶层）。
- **`Data` 的键**：

  | 键 | 形态 |
  |---|---|
  | `printId` / `printName` | 字符串（如 `3700000000000215` / `其他支出`） |
  | **`printSchema`** | **JSON 字符串**（要再 `json.loads`）→ `[0].cells[]` ＋ `[0].globalSettings{cols,rows,widths[{col,width}],heights[{row,height}]}` ＋ `sheetName` |
  | **`printSetting`** | **JSON 字符串** → `[0].printConfig{page,margin,headerFooter,paging}` |
  | `dataSetInfos` / `sheetProperty` / `globalProperty` / `workflowHistorySetting` | JSON 字符串 |

- ⛔ **响应里没有 HTML** ⇒ 任何"取回 HTML 再替换占位符"的实现**必然跑不通**（会在"取不到版式"上白耗时间，而真因是自己拿错了假设）。
- **`printId` 与单据类型的对应**（分流字段 = 主表 `PhidRecPayType_EXName`，**取值字面等于版式名**）：

  | 单据类型 | 版式名 | `printId` |
  |---|---|---|
  | **材料类** | **其他支出** | `3700000000000215` |
  | **外租机械类** | **付款通知书** | `3700000000000203` |

  ⚠️ **这组对应"与直觉相反"**（机器类的版式反而叫"付款通知书"）⇒ **改这里之前先核对《说明书》§4.6 的业务口径**。
- **模板 dataset id 常量**：主表 = `3700000000000010`；明细 = `{"3700000000000212", "3700000000000019"}`；单据级自定义字段 = `PaymentBill`。
- **几何参数**：缩放 `0.684` · 默认列宽 `110` · 默认行高 `30` · 默认字号 `14` · 行高倍数 `1.5` · 边框 `1.0` · 签名图高 `36`（设计 px → CSS px）。
- ⚠️ **框线用 CSS `border`**（四边独立、粗细统一）；⚠️ **`cellBorders` 某边未声明、或 `hide:true` ⇒ 不画线**（搞反会多出框线，用户从纸上就能发现）。
- ⚠️ Chrome 会把 border 宽度**取整**（0.68 / 0.5 / 0.35 都渲染成 1px）⇒ 要真变细只能**整体缩放局部坐标系**（外层 `transform:scale()` + 几何等比放大）。

### 9.6 签名（模板槽位 ↔ 审批流程）

- **节点名**：模板图片格 `cellData.dataFilter` 里的**节点名** ↔ 流程节点的 **`task_des`**（逐字相同）。
- ⭐ **`dataFilter` 有「两种写法」，两种都要认**（**同一套模板里混用**，实测两份模板各出现一种）：

  | 写法 | 形态 | 节点名在哪 |
  |---|---|---|
  | ① | `{"fieldId":"办理节点","value":"<节点名>"}`（建在自定义字段上） | `value` |
  | ② | `{"fieldId":"task_des","dataSetId":"workflow_history","value":"<节点名>"}`（**直接筛流程字段**） | `value` |

  ⚠️ **只认 ① 的后果不是"少印一个签名"，而是"那一格连签名槽位都不算"** ⇒ 它既不进"未命中"、也不进"流程未走到" ⇒ **其余签名都命中时它静默留白**（2026-09-16 实测踩到）。
- **签名图地址** = 同节点的 **`signature`** 字段（相对路径，带 `?s=<token>`）；`actionname` / `nodeid` / `username` 都对不上模板名。
- ⚠️ **缓存键 = 去掉 query 的 path**（`?s=<token>` 每次都变 ⇒ 带 query **永不命中**）；签名图**按人固定** ⇒ TTL 可取 15 天。
- ⚠️ **签名不是模板里的图片**，是流程历史字段；**模板哨位存在但流程没走到 ⇒ 留空是正确行为**。

### 9.7 打印机（IPP 直投）

| 通路 | 地址 | 应答 |
|---|---|---|
| **`ipp`（默认）** | **`ipp://<ip>:631/ipp/print`** | ✅ status ＋ job-id ＋ job-state ⇒ **可确认「打印机真的收件 / 打完」** |
| `raw`（兜底） | `<ip>:9100`（JetDirect） | ❌ **无任何应答**（发出去就不知道了） |

- ⭐ **真机实测机型 = RICOH IM 3000 PS3**（`printer-info` 自报）；`printer-state = Idle`；2026-09-16 用本工程的 `print/ipp.py` **一次连投 4 张成功**（付款通知书 ×2 ＋ 其他支出 ×2）。
- ⭐⭐ **唯一踩过的坑 ＝ 值标签（value tag）必须与属性的语义类型一致** —— 问题不是「打印机不支持某属性」，而是**报文非法**：
  **`document-format` 的类型是 `mimeMediaType` ⇒ 值标签必须是 `0x49`**。
  曾误用 `0x44`（那是 `keyword`）⇒ 这台机器直接回 **`0x0400 client-error-bad-request`**
  （响应仅 **115 字节**、`status-message` 只说 `client-error-bad-request`，**不指出是哪个属性错了**）。
  ⇒ **正解 ＝ 保留该属性、把标签改对**（实测 `0x0000` 成功出纸）；
  ⚠️ 排障中曾用「**整个删掉 `document-format`**」绕过（那也能出纸），但那是把报文改成**非标准形态**，**不要照抄**。
- **常用值标签**（RFC 8010 §3.5，**别记混**）：`0x42` nameWithoutLanguage · `0x44` keyword · `0x45` uri · `0x47` charset · `0x48` naturalLanguage · **`0x49` mimeMediaType**。
  ⇒ 本模块用的是：`attributes-charset` `0x47` · `attributes-natural-language` `0x48` · `printer-uri` `0x45` · `requesting-user-name` `0x42` · `document-format` **`0x49`**。
- ⚠️ **失败时必须把打印机自报的 `status-message` 带进错误文本** —— 只给一个十六进制状态码，
  现场**完全无从下手**（上面的线索**只**在那段文本里）。已落进 `print/ipp.py`。
- **IPP 状态码**（常用）：`0x0000` 成功 · `0x0400` **报文被拒** · `0x040A` 文档格式不支持 · `0x0500` 服务端内部错误 · `0x0503` 服务不可用
- **作业状态**：`3` 排队 · `4` 待处理 · `5` 打印中 · `6` 中断 · `7` 已取消
- ⚠️ 转 HTTP URI 时**端口不能省**（`ipp://ip:631/…` → `http://ip:631/…`）；
  但 **`printer-uri` 属性里带不带 `:631` 都行**（2026-09-16 只读隔离实测：两种写法同为 `0x0000`；机器自报的 `printer-uri-supported` 就是不带端口的形式）。
- ⚠️ **排障两个利器（都不会出纸）**：① `Get-Printer-Attributes`（`0x000B`）读机器能力与状态（`printer-state` / `document-format-supported` / `printer-uri-supported` 等）；② **`Validate-Job`（`0x0004`）只校验报文合法性、不打印** —— 用它**逐变量二分**最快。
  ⚠️ 若这两个操作也回 `0x0400`，**先怀疑值标签写错**，而不是「打印机不支持」。
- ⚠️ 打印机地址由**页面设置入口**填（见《说明书》§4.6 与 `PRD/02-功能规格/MOD-03.md` 能力 16），**取值不写进版本库**。
