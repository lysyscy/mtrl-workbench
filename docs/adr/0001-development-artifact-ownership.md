# 开发产物由项目与生产者负责管理

2026-11-06，用户通过 grill-with-docs 确认 Q1–Q6，并进一步明确 setup 继续负责规则与配套工具部署、升级，随后要求“开始”。本方案已批准实施，材料工作台为唯一先行项目；具体接入和验证状态沿[产物生命周期](../guides/artifact-lifecycle.md)核实，方案通过不代表已完成切换。

## 背景与取舍

当前开发输出默认进入个人 AgentArtifacts 目录，项目入口依赖个人安装的生命周期实现。它已有成功收尾、失败保护和限期证据能力；旧运行区、原生工具输出和业务运行状态仍分别存在。现场盘点发现发布成功后遗留的候选构建，也存在仍被业务待办引用的核对表和恢复点，不能将整个旧目录作为同一种临时文件处理。

本方案希望减少个人环境依赖和维护负担，保留活动消费者、唯一资料和业务状态的保护。采用项目默认出口，接受不同工作树可能各自产生产物的成本；共享缓存继续利用所属工具的能力。工具已具备的收尾能力优先复用。

## 已确认的方向

- **Q1，适用范围：**设计为各开发项目可采用的通用方案，以材料工作台为首个验证项目；其他项目逐个决定采用，不自动改造。业务资料、备份与运行状态沿所属机制管理。
- **Q2，输出位置与部署：**项目产物默认在项目内的 Git 忽略目录；执行中间文件使用系统临时目录；共享缓存沿所属工具默认位置。全局 AgentArtifacts 作为可选配置。用户进一步确认 setup 仍负责规则和配套工具向项目的部署、升级；项目的测试、构建、发布等开发命令使用已部署的固定版本，不在运行时依赖个人技能安装目录。
- **Q3，普通保留期：**成功后释放执行中间文件，必要证据默认保留 30 天。已确认可重新生成且不含唯一输入、未保存代码或待确认业务操作的开发失败产物，也允许按 30 天期限回收；需要继续调查的材料单独保护。
- **Q4，旧文件处置：**一次性分类收尾，分别处理可弃残留、仍需保留的证据和业务资料；不整体搬入新目录，不重新起算全部历史材料的保留期。无法判断的具名保留。
- **Q5，异常退出：**事先已声明且能核实为可弃开发产物的运行，确认生产者退出后可自动进入 30 天保留期。活动不明、唯一资料或业务结果不明仍保护，不能仅因缺少正常结束回执无限保留普通测试现场。
- **Q6，清理失败：**过期文件因占用或权限暂时删不掉，保留并报告清理结果，下次重试，不冒充本次测试或构建失败。新输出路径越界或归属无法确认时仍阻止该写入。

## 分类用语

以下是本方案的通用技术分类，放在本设计中，不扩入材料业务术语表。

- **执行中间文件：**仅供一次操作进行时使用的派生文件，其后续价值需在操作结束时判定。
- **可再生产物：**拥有足够的受保留来源与生成条件，可重新取得的依赖、缓存或构建结果。文件扩展名、目录名或进入 Git 忽略清单本身不证明可再生。
- **运行证据：**说明某次操作在特定版本、输入和环境下实际结果的日志、截图或报告；复跑产生的新证据不能代替原次事实。
- **业务与运行资料：**业务原件、未完成操作状态、备份、用户试用修改、在用版本及恢复依据，分别由所属业务或运行机制持有。

一次性脚本和实验原型须区分可弃过程与独有实现；仍有研究、复用或恢复用途时保留明确范围。分类按用途判定，不将“失败”统一解释为可删除，也不将“暂存”统一解释为永久保护。

## 目标目录与维护边界

```text
项目/
  .artifacts/runs/<run-id>/
    run.json                 # 自动生成的本次身份、用途、结果与保留信息
    logs/ reports/           # 按实际输出创建，不预建空目录
    screenshots/ traces/     # 需要留证时才产生
    work/                    # 跨进程交接、待启动或在用预览等有消费者的工作目录
系统临时目录/<project>-<run-id>/
                            # 单次操作中的可弃计算文件
```

旧 `.artifacts/active`、`.artifacts/archive` 和已登记 AgentArtifacts 继续服务旧运行，按下文一次性收尾；新运行默认只写 `.artifacts/runs`。`.scratch` 继续持有当前任务材料，源码与文档不纳入证据过期删除。依赖和缓存沿 Python、pnpm 等原生位置，不复制进每次证据目录；在用虚拟环境仍按服务运行资源保护。

setup-solo-workflow 继续负责将规则与配套工具部署、升级到获准项目，固定来源版本并完成相应核验。项目的开发入口及其运行所需代码随仓交付，日常命令直接使用已部署版本，不从个人 `.skills-manager` 目录加载。共用实现仍有唯一维护源，项目中的已部署副本不成为另一份独立维护源；通用修改回维护源，经 setup 按批准范围更新。这里的部署指开发规则与工具接入，正式应用发布仍沿项目现有发布入口和当次授权。

复用现有边界检查、租约和清单保护，仅调整分发与输出方式，不另建并行清理器或包服务。

可配置仓外证据根，但必须显式建立项目归属。每棵工作树具有独立运行身份和默认输出，清理限自身登记范围；共享根须区分工作树，不能只用分支名定位。链接不作为扩大扫描范围的入口。

## 日常运行与自动收尾

普通开发命令自动建立运行记录、持有消费者保护并收尾。用户和 Agent 不必为每次测试额外执行登记、租约和关闭三步；保留现有显式入口供排查和特殊任务使用。记录只保存必要的任务名、版本或输入指纹、运行身份、用途分类、消费者、操作结果、结束/到期时间与保护原因，不保存凭据、业务原文或完整环境。

| 情况 | 处理 |
|---|---|
| 成功且消费者已结束 | 释放可弃中间文件；必要报告、日志和选定截图从用途结束时起保留满 30 天 |
| 普通开发失败，无唯一资料或未决业务后果 | 保留必要排障证据及有价值的失败现场，运行结束后保留满 30 天；无需保留的依赖缓存不复制归档 |
| 生产者异常退出 | 核进程身份及实际消费者；仅对已声明可弃的运行，在首次可靠确认用途结束时记录终点，再起算 30 天；无法确认则保护 |
| 明确继续调查或验收 | 只保护所需文件或最小关联组，写原因与解除条件；按现有复查机制提醒，不到期强删 |
| 活动消费者、唯一输入、未保存源码或业务结果不明 | 保持保护，交所属任务或业务机制确认 |
| 过期清理失败 | 保留未成功删除部分，记录失败并稍后重试；不重复宣称已删除 |

期限不按文件修改时间推断，读取文件不续期，复制或换目录不重置历史到期日。解除保护须先核用途结束；已到期证据沿现行缓冲规则保留必要时间。一次运行可正常完成而清理未完成，两个结果独立可见。

系统临时目录仅承载允许丢失的中间件，不承诺跨重启留存。需要保留 30 天的日志、失败证据直接写入项目证据目录；不能只在报告里留下一个已删除的临时路径。一次性脚本的独有实现、待采用原型及未保存输入，不能因创建在临时目录就被认定可弃。

预览构建和跨进程发布候选仍使用受归属校验的 `run/work`，保留现有路径及散列核验。构建命令结束不等于待启动或在用资源用途结束；由预览、发布消费者释放。正式发布确认完整副本已加载后，候选才可退出；`var/frontend/releases` 继续由发布器保留当前和上一完整版本。试用数据、数据库备份及业务操作状态不交给本清理器。

保留现有每日清理方式，由明确配置的入口调用项目自身的清理能力。试点切换时只调整获准项目的目标，其他项目保持原登记区；不扫描整盘发现项目、不按目录名接管旧文件。成功安静运行，失败或保护状态发生实质变化时沿现有通知方式反馈；不把清理接入每次提交或新增 AI 定时巡检。

## 清理边界与失败反馈

自动清理只接受本项目明确拥有、已结束、到期且无保护或活动消费者的产物。沿现有机制复核绝对路径、链接、记录、清单及散列；新增未知文件、内容漂移、损坏记录或无法核实的锁保留相关现场。未知文件不因藏在 `.artifacts` 或 Git 忽略目录就获得删除资格。

生产者自身的退出码保持原意；清理警告进入独立结果和必要提示。显式清理命令未完成时返回非零，方便调度检测。禁止因清理失败伪报测试失败或发布失败，也禁止只报告操作成功而隐藏清理未完成；没有安全输出位置时，应在真正执行前拒绝该次写入。

## 旧文件的首次收尾

实施时复核盘点快照和实际消费者，形成同一批处置范围：

1. 旧路径已失效的一次性脚本、正式发布已不再消费的候选构建：核独有内容与用途后退出。
2. 仍需保留的历史报告：保原用途与到期日，原位到期或连同引用迁移，不整批续期。
3. 原型源码和可重建依赖分别判断，保留所需源码与版本依据；不能为释放依赖顺带删除未保存实现。
4. 油卡核对表、试用恢复点、原始输入、正式导出和数据库备份沿原主人保留；导入预览 JSON 须先核业务操作与现行消费者，不凭数量清空。
5. 无法判断的具名保留，写明具体材料、原因与解除条件；旧根清空及无消费者前，不撤销其登记或停止所需清理。

每批只在获得实施授权后处置；新生产者与旧现场的迁移分别验收。迁移前固定文件身份，迁移后核内容、引用和消费者，再退出原位置；不搬动正在使用的资源。

## 实施顺序与验收

1. 由 setup 将固定版本的配套工具部署到试点项目，使开发命令独立于个人技能安装目录，并保留现有保护能力；使用独立临时测试根验证，无需改正式业务数据。
2. 接入新输出分类及独立结果反馈，选择后端验证、前端构建/预览/发布三条代表链；复用已有测试，仅补真实覆盖缺口。
3. 核正常结束、普通失败、异常退出及文件被占用四种场景：证据可定位、保留期正确、在用资源不误删、原操作结果不被清理结果覆盖。
4. 在新旧路径并存条件下验证工作树隔离、链接/散列漂移保护、历史期限保持及未知文件保留；然后衔接试点每日任务，核一次真实调度结果。
5. 获准执行旧文件分类收尾，核每批实际剩余和保留理由。试点验收后再决定其他项目采用范围。

设计验收还包括一项体验要求：日常任务使用原测试、构建和发布入口，结束回执给出可直接定位的结果路径；不要求使用者记住一套额外生命周期步骤。任何未执行的验证、未能退出的材料或未获准项目分别列明，不以试点成功宣称全局完成。
