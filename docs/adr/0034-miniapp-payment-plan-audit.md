# D34 · Mini App 只做付款原表核对，不加后端端点

> 读者：接手这个 Mini App、或问「为什么会有第三个前端」的人与 Agent。回答：Mini App 的定位与边界、为什么不加后端端点、与 React 重做的关系。何时读：动这个 Mini App、动付款原表核对链路，或有人提议把功能扩进 Mini App 之前。状态：**已定稿**（2026-10-22 用户对齐；**实施尚未开始**）· 规格见 `.scratch/miniapp-payment-plan-audit/spec.md`。

**落地位置**：`.scratch/miniapp-payment-plan-audit/spec.md`、`skills/payment-plan-audit/SKILL.md`（核对口径主人，未改）· 同批改：`docs/adr/D索引-D1-D32.md`（索引加一行）、`docs/status.md` §13.6（交接行）

## 决定

建一个 Mini App「付款原表核对台」，把「付款原表核对」这条每月流程（取快照 → 判定项目归属 → 标注原表 → 回写拟付款方式）收进一个页面。**它长期与现有前端、React 重做并存**，但只覆盖这一条线。

三条硬边界：

1. **不新增任何后端端点** —— 只调既有的 `GET /api/m03/plan-audit/snapshot` 与 `POST /api/m03/plan-audit/methods`。
2. **不重写技能脚本** —— 只调 `skills/payment-plan-audit/scripts/`，匹配规则与核对口径仍由该技能的 `SKILL.md` 持有。
3. **不接管付款动作** —— 第 4 步「复制单据号 → 系统付款通知书页粘贴勾选」原样保留；技能与 Mini App 都不代替用户选付款对象、打印或登记付款。

## 为什么

**为什么不加后端端点**：付款原表核对的后端本来就有「预览—确认—提交」三段式，`methods.py` 的写入前校验链（预览指纹、快照指纹、单据原值、审批/已付金额）已经是完整的业务护栏。再加一个端点等于把这套护栏复制一份，两份迟早分叉。

**为什么不重写脚本**：核对口径（金额、审查规则、汇总口径、付款方式对应）在这套技能里已经积累并有测试。Mini App 是**界面与编排层**，不是第二个规则主人。

**为什么不扩成全功能**：Mini App 存在的理由是把「终端命令 → 磁盘中间文件 → 口头确认」这条来回跳压平，不是再造一套全功能前端。全功能已有两个主人：现行壳与 React 重做。

**为什么与 React 重做并存而不是等它**：用户 2026-10-22 明确「重做只是前端重做，功能上可以说没有任何变化」；而这条月度流程每月都要跑，不能等。代价是两份前端要长期跟住同一批后端行为 ⇒ 约定 **后端行为变更时两边同批同步**。

**为什么机械费不进 Mini App**：它的每一步成本是「判断」而不是「点几下」，Mini App 省不了主要部分；而要做，要么改既有技能的「目录批次」口径（单文件入口），要么撞上 `D26`「导入只留通用面」。本次范围外，将来另立 effort。

**为什么不与 `D26` 冲突**：`D26` 约束的是**导入面**（`/api/imp/*` 与页内向导）。本 Mini App 不碰导入面，只做付款原表核对，**不构成第二个导入入口**。

## 后果

- 需要向宿主申请 `agentAccess: "session.run"`（唯一合法值是字符串，不是数组）才能让页面侧跑 Agent；页面侧跑的是**所在聊天会话的 Agent**（带科室技能），Node 侧跑主 Agent。宿主当前会话上下文**传不进去**。
- 通行凭证各存各的：Mini App 存宿主隔离的 `context.dataDir`，命令行技能仍用 `~/.mtrl-workbench/` 那份；`--session-file` 已贯通全部脚本，所以**一行现有脚本都不用改**。
- 归属判定沿用既有硬约束：**Agent 判、必须给依据、必须覆盖原表每一个项目**；但判定结果要在页面上由用户确认后才继续。
- 真实写入（拟付款方式回写）**只在用户明确点头的那一次**执行；其余环节一律零写库。
- 本决定只覆盖**定位与边界**；具体界面、接口与验收口径在 `.scratch/miniapp-payment-plan-audit/spec.md`。
