# 开发治理整改规格：可信文档、清楚进度、按影响核验

> **读者**：项目负责人及逐票实施整改的 agent。
> **回答**：整改需求、范围、实施取舍、验收与跨会话接手依据。
> **何时读**：领本次整改执行票、判断边界、核验结果及新上下文接手时。
> **状态**：已定稿（用户已确认需求与 A→B→C→D 顺序；to-spec/to-tickets 准备已完成；实施状态以各执行票为准）。
> **日期**：2026-10-07。**关联**：TAIL-246 / TAIL-247 / TAIL-248 / TAIL-249；既有 TAIL-228 / TAIL-235 问题及 TAIL-245 实测。
> **分诊**：ready-for-agent；实施状态以执行票为准，本件不是另一份进度台账。

## Problem Statement

用户已开始自用、边用边改，但难以信任当前文档能正确指导 agent。
过期说明、重复口径、矛盾与漏改造成接手误导；大量文档与检查工具维护票遮住真实待办。
普通改动承担与结果无关的治理核验，等待时间长，用户看不清开发计划、进度及确认方式。
清晰、可理解的目录结构能让用户知道资料在哪里，也提供判断 agent 是否读对资料的安全感。

**订正助手此前的误解**：用户要减少的是现存无用文档和现存不合适的票。
在良好文档体系下，未来必要的文档与票可以正常产生；本次跨会话整改正常走 Matt 主流程。
不以“少建文档或少开票”作为独立目标，也不以“一张旧票换一张新票”作为整改方式。

## Solution

用户有可信的目录地图和现行文档说明，能从明确入口看到当前可用能力、欠缺、计划与进度、本次改动和结果确认方式。
agent 通过简短入口按需读取现行口径，历史材料可追溯但退出默认接手阅读路径。
旧票按真实需求、已完成证据、重复或过期情况重新处置，实际业务与数据安全待核项继续可见。
普通改动用与影响后果相称的核验，以约一分钟为目标；关键改动保留完整核验。
每项跨会话工作都有自足执行票、明确阻塞边与唯一规格，新对话不依赖旧聊天记忆。

## User Stories

1. 作为项目负责人，我希望知道每个目录的用途，从而能理解项目布局并检查 agent 是否找对资料。
2. 作为项目负责人，我希望看到每份现行文档的一句话用途，从而知道该查哪份而不必逐份读全文。
3. 作为项目负责人，我希望历史和临时资料按类别说明，从而能追溯且不被大量文件名淹没。
4. 作为接手 agent，我希望默认入口只指向现行规则，从而避免用过期说明做决定。
5. 作为接手 agent，我希望每条规则有明确维护位置，从而改动时能找到正文及受影响引用。
6. 作为项目负责人，我希望看到现在能用什么，从而知道当前系统能承担哪些工作。
7. 作为项目负责人，我希望欠缺与未核实事项分开显示，从而不把没验证误认为没实现或已完成。
8. 作为项目负责人，我希望开发计划和实际进度一致，从而能判断下一步及阻塞原因。
9. 作为项目负责人，我希望知道本次在改什么和如何确认结果，从而不用学习整套治理机制。
10. 作为项目负责人，我希望旧票能取消、合并或据证完成，从而不会仅因曾经立票就继续无用工作。
11. 作为项目负责人，我希望真实业务需求和未证明的数据安全事项继续可见，从而不会被清理旧票顺带丢失。
12. 作为开发者，我希望普通改动仅承担必要核验，从而尽快交付可复验结果。
13. 作为使用者，我希望金额、批量写入、权限等关键改动充分核验，从而降低实际使用风险。
14. 作为开发者，我希望无关治理问题不阻挡普通改动交付，从而避免一个小改动扩大为全仓整改。
15. 作为接手 agent，我希望选择遗漏、执行失败和未知范围能被发现，从而不会把没验当成通过。
16. 作为项目负责人，我希望普通核验报告实际范围和耗时，从而知道一分钟目标是否真的达到。
17. 作为开发者，我希望未来必要文档和票正常产生，从而让新工作有记录且能跨会话接手。
18. 作为接手 agent，我希望执行票能独立理解目标、验收、前置和边界，从而在新上下文中完成一项工作。
19. 作为项目负责人，我希望通用前端经验与本项目范围区分，从而避免重新设计已经定型的功能。
20. 作为项目负责人，我希望整改未达成项如实呈现，从而不会把局部提速或形式全绿当成整项完成。

## Implementation Decisions

- 保留一份整改规格作为跨会话依据；工作按已确认的四个可独立验收结果拆为执行票，不另建重复母规格。
- 第一项核实真实状态并处置旧票；第二项完成可信地图、现行文档清单及归档衔接。
- 第三项在已明确的现行规则和阅读范围上安排按影响核验；第四项用新上下文验收整体接手与开发体验。
- 依赖链为 A→B→C→D：状态处置决定现行资料；现行资料和规则范围决定检查安排；最终试跑验收前三项结果。
- 实施时长期规则更新现有主人文件；状态入口和各索引只维护各自职责，不手工复述同一结果。
- 现行文档逐件说明，历史与临时资料按类别说明；不强制每个目录新增说明文件。
- 先核实正文是否仍生效及其引用，再归档或删去无用材料；保留必要历史追溯和可恢复基点。
- 正式待办承载明确需求、确认缺陷与有证据的风险；尚未决定的优化作为建议，未来必要工作照常形成票与文档。
- 检查是否阻挡交付按本次结果、业务规则与数据安全的后果判断；工具自身失败先判定其守护范围。
- 选测以实际输入和影响范围为依据，保留完整入口及无法证明范围时的兜底；局部核验不刷新权威结果。
- 变异自证随对应判据变化及必要风险运行，共用靶串行；减少重复执行不能依靠并发抢写或放宽预算。
- 无新业务接口、数据库结构或前端流程变更；不修改个人全局 skills。
- 每张执行票适合一个新上下文，完成后核验和两轴 review；提交仍需用户点头。

## Testing Decisions

验收沿用用户已确认方案的边界：目录与入口找得到可信资料，普通检查报告实际范围和耗时，关键路径完整，真实使用待核项不丢失。
优先利用现有文档引用检查、选测入口、自测和反向见证，不预设新增测试框架或全仓审计工具。

- 状态与旧票：逐项对照实际资料、代码或运行证据，核对已完成、未核实、取消及待做的区别。
- 文档与地图：核对现行清单和实存文件；从入口复演找状态、业务规则、核验命令、旧决定四条路径。
- 选测与执行：在命令行入口验证真实运行与跳过的结果，制造应跑却漏选、清单外选择及关键/未知输入情境。
- 失败与权威档：验证失败不生成通过证明；局部执行前后权威结果档不被改写。
- 耗时：同一环境、明确普通改动，记录冷启动与已有证明条件、实际检查范围及总耗时；以约一分钟为目标。
- 完整路径：用关键改动情境验证完整入口真实可执行，不能只断言选择清单长得正确。
- 跨会话：独立读取规格、当前票与入口后说明任务、前置、范围及确认方式，再完成必要的可复原试跑。
- 文档整理使用相关文档检查；检查机制变化使用有意义的漏跑见证及完整核验，不为低风险文字修改增加镜像测试。

先前相关核验优化只证明部分重复检查可省，不构成本规格一分钟目标的验收。
目标未达到必须标未达成并报告原因，不自动放宽目标或宣称整项完成。

## Out of Scope

- 本项目现有前端重画、跨页流程改造及新业务功能开发。
- 为完成旧票而推进全仓逐条规矩扫描、固定拆分文档或推测性架构优化。
- 逐个解释全部历史文件和工具脚本，强制逐目录说明文件或新目录尺子。
- 禁止未来正常产出文档和票，或把所有新工作强行塞进同一张票。
- 在本轮准备阶段执行旧票撤销、文件归档、检查机制修改、实现或提交。
- 自动发送信息到外部平台，或建立新对话代替用户自己交接。
