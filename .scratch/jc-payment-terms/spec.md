# 集采账期提醒与付款方式

业务方案及三票拆分：用户于2026-10-23确认。规格状态：TAIL-432—434源码及隔离验收完成，独立分支codex/jc-payment-terms；正式迁移及后端部署未执行。实际静态付款404兼容已核；技能中央库及原五份安装均已更新；豆包按用户授权不备份重建，并落实以后同类受管副本自动恢复，详见434 Comments。

基线：master `b6d597639030b43b177c8e43da4b86b1346fbe8f`。本次仅整理规格；正式业务迁移、部署与服务重启仍须另行授权。

## Problem Statement

集采账期和付款方式混在备注里，付款时容易漏看。历史发票日期大量来自导入当天，直接据此提醒会误报。用户以Excel付款计划为操作入口，需要既能发现计划误填的付款方式，又能保留经确认的特殊付款安排。

旧前端需要先使用这项能力，新前端重构后应复用同一后端判断。通知书只关联合同，无法把付款可靠分配到某张发票，因此本次只做合同层面的付款前提醒。

## Solution

集采合同新增账期和付款方式，迁出备注中的明确内容。后端统一提供账期提醒和付款默认方式，旧付款窗口先接入。付款计划核对技能在用户Excel中标出与合同不一致的方式；正常行继续处理，经用户确认的付款计划优先于合同默认方式。

## User Stories

1. 作为材料工作台使用者，我希望在合同台账填写账期，以免每次从备注推断。
2. 作为付款人，我希望按账期最大天数核对发票日期，以便只看到尚未满账期的提醒。
3. 作为付款人，我希望提醒随所选付款日期变化，以便安排实际付款日。
4. 作为付款人，我希望仍能确认未满账期的付款，以便执行已商定的提前付款。
5. 作为付款人，我希望多张发票只触发合同层面的核对提示，以免误把合同欠款当成某张发票的到期可付金额。
6. 作为使用者，我希望已付清、无欠款的记录不再产生付款提醒，以免重复干扰。
7. 作为合同维护人，我希望约定付款方式使用现有四种候选，以便与付款窗口和Excel计划核对。
8. 作为Excel计划核对人，我希望付款方式冲突标在原Excel里，以便在熟悉的位置修正。
9. 作为Excel计划核对人，我希望冲突行暂不回写而正常行继续，以免一行问题阻断整批。
10. 作为付款人，我希望已确认计划中的特殊付款方式优先，以便继续以Excel为主安排付款。
11. 作为付款人，我希望窗口中的手动选择不会被默认值刷新覆盖，以便完成本次操作。
12. 作为合同维护人，我希望迁出账期、付款方式后保留其他备注，以免丢失质保金或分阶段付款约定。
13. 作为合同维护人，我希望重新抓取不会覆盖人工维护的合同信息，以免反复修正。
14. 作为使用者，我希望只为有欠款且能明确匹配的历史发票补正真实日期，以免进行无用抓取。
15. 作为新前端维护人，我希望复用同一后端结果和字段，以免重构上线后丢失这项功能。

## Implementation Decisions

### 合同字段及人工维护

- 新增独立账期字段，显示为`x±y天`，按自然日计算，最大天数为x+y；固定60天按`60±0天`表达。对输入进行必要格式及非负数校验，不扩展自然月、约定付款日或分阶段账期引擎。
- 新增合同约定付款方式，候选为现汇、承兑、供应链、其他；空值表示未填写约定。现存旧付款条件字段已退出使用，不能把它直接当作四值枚举。
- 保留人工维护的账期、付款方式及剩余备注，后续抓取或导入不覆盖这些人工值。

### 付款前账期提醒

- 起算日期采用发票子表日期。有贸易公司的合同使用贸易发票日期，其他合同使用供应商发票日期；不在两侧重复计算。
- 比较日采用付款窗口所选付款日期。付款日期不晚于“发票日期＋最大账期天数”时提醒；超过该日不再提醒。例如90±10天按100天计算，第100天仍提醒，第101天不提醒。
- 多张发票中只要存在一张未满账期，提示“该合同存在未满账期的发票，请核对本次付款”，并提供核对所需的合同、账期和相关日期依据。不推断本次付款对应哪张发票，不计算到期可付金额。
- 仅对仍有欠款、尚未付清且具备账期和相应发票日期的记录进行判断；无账期或无发票时不弹账期提醒。复用现有欠款及实际付款校验口径，不另造金额口径。
- 本次只提醒，付款人可继续确认；保留现有余额、金额、幂等及事务校验。
- 不新增日期真实性标志、日期待核实状态或人工到期日功能。一次性抓取未匹配到的旧日期保持原值，不增加特殊处理。
- 旧前端读取后端统一结果，在现有付款确认流程展示；变更付款日期后重新判断。新前端以后使用同一接口和响应含义。最终接口、字段及提示依据在实施票中记录供重构同步。

### 付款方式优先级

- 付款窗口初始值依次为：已确认付款计划方式、关联合同方式、现汇。
- 复用通知书已有拟付款方式字段保存已确认计划。字段为空时的默认现汇仅是操作便利，不代表合同约定或已确认计划。
- 打开窗口时取得默认值，窗口内手动修改后保留用户选择；不随后台默认值刷新覆盖。最终确认时仍可改用其他方式。
- 合同默认方式动态读取；历史已发生流水中的实际付款方式保持原记录。

### Excel付款计划核对

- 核对对象是用户Excel付款计划中的方式与关联集采合同的约定方式。i8抓取付款单没有付款方式，不以系统默认现汇冒充i8原值。
- 复用现有核对快照、Excel标注、备份、预览确认和受保护的拟方式回写能力，按需要补充合同关联与约定信息。
- 方式不一致时，在原Excel按既有问题单元格及说明列规则标出，暂不回写该行方式；正常行继续处理。合同未填方式则标待核实，并暂不回写该行方式。
- 用户修正Excel或明确确认该行是有意采用的其他方式后，按正常确认流程回写该计划方式；付款窗口优先采用它。沿用现有预览确认和防过期校验，不建设额外异常审批系统。
- 保持原Excel业务值、公式、人工批注及打印布局；不增加另一套网页核对结果作为操作入口。

### 备注迁移

- 先产生实际合同逐条迁移前后对照，经用户确认后才改真实业务数据；已填写的新字段不被迁移覆盖。
- 只迁移明确的账期、付款方式片段，保留其他文本与模糊表达。银行承兑、银承归为承兑；不能明确转换成天数的阶段、月份、验收或质保条款保留备注。
- 示例：`90±7，银承，5%质保金一年`迁为账期90±7天、方式承兑，备注保留5%质保金一年。
- 示例：`60天，承兑`迁为账期60±0天、方式承兑，备注清空；`发货前95%，5%质保金，银承`只迁出承兑，其他内容保留。

## Testing Decisions

- 优先从现有业务API及核对技能的Excel输入输出验证外部行为，复用合同维护、批量付款、拟付款方式和原表核对的既有测试接线。
- 在独立测试库或schema验证合同字段保存、抓取保护，以及备注迁移保留其他文本、不覆盖人工值和重复执行安全。
- 付款提醒覆盖最大天数的当日与次日、付款日期变化、供应商与贸易发票选择、多张发票、已付清和缺少账期/发票。确认提醒不改变允许付款与现有校验。
- 付款默认方式覆盖计划优先、合同次之、现汇兜底，以及用户在窗口手改后不被覆盖。
- 核对技能使用小型脱敏Excel验证冲突行标记并跳过、正常行继续回写、用户确认例外后计划优先，并保留既有备份、指纹和防过期保护。
- 旧前端做针对性付款窗口和台账交互检查；不为此增加全仓审计或测试矩阵。真实迁移及部署现场与隔离验证分别报告。
- 一次性i8补日期按用户要求不建专门测试或持久抓取留痕；不能把目录匹配成功当作已读到真实发票日期。
