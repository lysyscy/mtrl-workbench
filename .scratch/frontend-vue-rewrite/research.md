# React 表格稳定性：一手资料研究

> 当前状态：449已由用户人工确认通过并关闭，费用等待取舍已接受；实际覆盖及客观未验边界回[验收证据](evidence.md#用户验收与关闭2026-10-27)与[原票](../tails/issues/TAIL-449-全站加载与表格尺寸稳定统一.md)。下文保留研究形成时的只读结论与暂停背景，不作为当前暂停指令或全站完成证明。

> 研究日期：2026-10-26。用途：供本轮全站表格方案整合；属于只读研究与建议，不是实施规格或已验收方案。只新增本文件；未改源码、预览、服务或业务数据。已整合 AG Grid 36.2 对应版本官方文档与本机安装包核对；已落[TAIL-449](../tails/issues/TAIL-449-全站加载与表格尺寸稳定统一.md)，用户要求先讨论通知书关联入口，当前暂停实施。

## 结论与边界

跨框架的一手资料支持同一方向：**把尺寸准备移到内容首次可见之前，以已经确定的列宽计算完整内容所需高度；后续更新保留可用画面和编辑状态。** 去掉动画、增大估计行高、等待字体或套骨架，各自只覆盖链路的一部分，不能独立保证表格稳定。

这里的“一步到位”可以是全站共用一套尺寸准备、首次展示与更新规则；不能据此承诺任意动态内容都能零成本、零等待、精确预知高度。行高依赖实际内容、列宽、字体、字号、内边距及控件。估计值仍然是估计值；精确值需要已知且一致的渲染条件，或者实际测量。下列项目建议属于对官方资料和本项目诊断的推论，不应归为厂商已经验证的项目方案。

现有诊断基线为 [table-geometry-summary.json](../../.artifacts/active/react-writable-preview/20261025-admin-i8/reports/table-geometry-summary.json)，记录 HEAD `b6d84804691f096f07add1d735514a3c1207a2f1`、8065 及默认尺寸随后改写的机制。文件明确限定默认只读视图覆盖，并指出字体阻断没有消除重排。本研究未重跑浏览器、未独立复核当前运行 HEAD，也不把旧 8060 的分数当作 8065 结论。

必须保留 [前端设计约束](../../docs/guides/frontend-design.md)：完整长文本和金额、现有列序、必要换行、字号档位、焦点与草稿；编辑期间保持列宽；普通筛选/排序/刷新不做整表淡入淡出或行位移动画。MOD05 换项目必须隐藏旧项目数据和编辑入口，因此“保留画面”限于同一业务范围的后台重读，不能展示旧项目数据冒充新项目结果。

## 一手证据与项目推论

### E1. 预留空间与合适的首次展示能减少突发位移

**官方结论：** 动态内容应提前预留足够空间，可以用占位或骨架；无法知道精确高度时，预留空间本身也存在空白与残余位移的取舍。移除已经预留的空间同样会造成位移。已知尺寸容器内替换内容是官方列出的办法之一。

来源：[web.dev — Optimize Cumulative Layout Shift](https://web.dev/articles/optimize-cls#ads_embeds_and_other_late-loaded_content)。

**本项目推论：** 先稳定页头、工具条和表区外框；保持既有全高主工作区与内容自适应短表的区别。占位不应显示一组默认窄列/矮行，再让真实数据把它们撑开。表区稳定不代表内部列宽、表头和行高已稳定，必须分别验收。

### E2. 字体 ready 是当前已使用字体的完成信号，不等于整套字库或未来内容已准备好

**官方结论：** `document.fonts.ready` 等待当前已使用字体的加载及相关布局完成；已使用字体可以与声明字体不同。`FontFaceSet.load(font, text)` 可触发指定字体加载，`text` 根据 unicode-range 限定匹配字体面，但不验证每个字形确实被覆盖。

来源：[MDN — Document.fonts](https://developer.mozilla.org/en-US/docs/Web/API/Document/fonts#doing_operation_after_fonts_are_loaded)、[MDN — FontFaceSet.load()](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/load#parameters)。

**本项目推论：** MiSans 分片应针对本次表头和准备测量的实际文本/字重就绪；不能在文本尚未进入使用集合时等待一次 ready，就宣称随后所有中文都不会触发新字体。字体失败要有明确可用降级，不能永远阻塞表格。仅等字体不能解决尺寸异步改写。

### E3. 字体速度、品牌外观与换字稳定性存在真实取舍

**官方结论：** 字体交换因度量差异可能引起重排；`font-display: optional` 可避免迟到交换，但迟到时本次访问可能不使用目标字体；`block` 延迟文字显示，也仍可能因不可见回退字体的占位差异而重排。unicode-range 分片可按内容取用；preload 会绕过 unicode-range 的部分选择逻辑，应谨慎使用。

来源：[web.dev — Best practices for fonts](https://web.dev/articles/font-best-practices#choose_an_appropriate_font-display_strategy)。

**本项目推论：** 保留已批准的 MiSans 与官方分片机制，先检查关键片段发现时机和实际请求。不要把全量预加载/等待全部字库当通用免费方案，也不能未经体验裁决用 optional 让部分首次访问改用另一字体。回退度量匹配可降低风险，但不能未经真实中文换行检查就声称完全相同。

### E4. React 可以在绘制前完成测量与纠正，但这会阻塞绘制

**官方结论：** `useLayoutEffect` 在浏览器重绘之前运行，允许先渲染、测量、再以正确尺寸渲染，使用户不看到中间位置；其中执行的代码和状态更新会阻塞重绘，过量使用会让应用变慢。

来源：[React — useLayoutEffect](https://react.dev/reference/react/useLayoutEffect#measuring-layout-before-the-browser-repaints-the-screen)。

**本项目推论：** 有限且有界的首次尺寸校正可以在显示前完成；这不是“把全部测量搬进 useLayoutEffect”或对整份大数据同步反复测量的依据。实际依赖异步布局的第三方表格，不会因为外面包一个 Hook 就自动同步完成。

### E5. 首次加载与已展示内容的更新应采用不同策略

**官方结论：** Suspense 可以协调首次内容一起揭示；已显示内容更新时重新切换为 fallback 会造成突兀体验。Transition 或 deferred value 可在合适的非紧急更新中保留已显示内容。Suspense 不会自动检测在 Effect 或事件处理器内发出的取数。

来源：[React — Suspense: Preventing already revealed content from hiding](https://react.dev/reference/react/Suspense#preventing-already-revealed-content-from-hiding)、[同页 Caveats](https://react.dev/reference/react/Suspense#caveats)。

**本项目推论：** 首次无可用数据时展示稳定等待态，尺寸准备后一次揭示；同范围刷新继续展示当前表格，局部标识重读中，保留行 ID、滚动、选择、焦点和草稿。实现可复用现有取数状态，不要求引入 Suspense 或更换路由/请求架构。跨项目数据的可见性按本项目约束处理。

### E6. 其他成熟网格同样承认 auto 行高与虚拟化的估计修正成本

**官方结论：** MUI 动态行高采取 lazy 测量：未渲染行先用估计高度，渲染后替换为实测值，滚动条滑块可能变化；`getEstimatedRowHeight` 只能改善估计。auto 行高默认禁用列虚拟化以正确测量所有列；重新启用列虚拟化则仅依据可见列测量，横滚时行高可能变化。

来源：[MUI X — Data Grid row height](https://mui.com/x/react-data-grid/row-height/#dynamic-row-height)。

**本项目推论：** 换表格库不会天然消除这一约束。长文本不能截断时，必须明确哪些列影响行高、什么时候获得其完整宽度和高度；仅保证首屏无抖动不能推导之后滚动也无修正。MUI API 属于 MUI，不能直接用于 AG Grid。

### E7. 估计与精确测量应由同一尺寸模型协调

**官方结论：** TanStack Virtual 的 `estimateSize` 可以给出实际尺寸，或在动态测量时给出估计尺寸；动态测量场景建议采用舒适范围内较大的估计，以改善初始位置。官方同时警告：同一项同时由手动 resize 与自动 measure 改尺寸会产生不可预测行为。

来源：[TanStack Virtual — Virtualizer, estimateSize / resizeItem](https://tanstack.com/virtual/latest/docs/api/virtualizer#estimatesize)。

**本项目推论：** 全站应只有一个尺寸决策入口，避免页面测宽、共享适配、字体回调、表格 auto-height 各自写同一尺寸而互相打架。估计改善用于尚未测量的区域，不应当作精确预计算。这里只借鉴其机制；TanStack latest 的新选项、滚动修正能力和缓存 API 均不视为本机 AG Grid 已具备。

### E8. 骨架适合首次结构化内容加载；局部重读应局部反馈

**官方结论：** Carbon 把 skeleton 用于首次加载的容器与数据组件，包括数据表；内容到达就应消失。局部组件处理适合 inline loading，整屏处理才使用整屏加载反馈。其通用模式没有给出一个适用于所有页面的“延迟 X ms 显示骨架”最优值。

来源：[Carbon Design System — Loading](https://www.carbondesignsystem.com/building-blocks/core/patterns/loading)。

**本项目推论：** 等待态应复用已知表区外框与列分区，不给每个按钮和输入框套骨架。短请求可不闪现骨架；是否延迟、延迟多久，需要依据实际首屏完成分布与视觉检查决定。不要人为延长已完成加载来播放骨架，也不要把“加载中”伪装成无记录或零金额。

### E9. 降低动态效果是用户偏好，不替代稳定布局

**官方结论：** `prefers-reduced-motion` 表示用户希望移除、减少或替换非必要动效；大物体的缩放和平移可能使部分用户不适。

来源：[MDN — prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)。

**本项目推论：** 稳定的首次展示在普通和减少动态效果模式下都必须成立；减少动态效果时骨架呼吸/扫光和非必要出现动效也要关闭或换静态提示。无需通过整表缩放或位置动画掩盖尺寸修正。

### E10. CLS 不能单独证明表格看起来稳定

**官方结论：** CLS 对离散输入后 500ms 内的位移可排除计分，滚动/拖动不属于这种 recent input。良好动效可能帮助解释状态变化，但 transform 动画不触发布局位移；因此“低 CLS”与“没有可见运动”不是同一个命题。

来源：[web.dev — CLS: Expected versus unexpected layout shifts](https://web.dev/articles/cls#expected_versus_unexpected_layout_shifts)。

**本项目推论：** 验收同时记录 CLS 与实际列宽/行高/表头高度变化、阅读锚点和焦点变化。不能只看加载 Lighthouse 分数，也不能通过改变发生时间或使用 transform 让指标不计分，就宣布问题解决。

### E11. AG Grid 36.2 的自动行高本身采用延迟测量

**官方结论：** autoHeight 只测量已渲染行，因此新行进入 DOM 时行高、行位置与滚动范围可能调整；这是 lazy height calculation 的必然结果。autoHeight 列增加尺寸监听且停用该列的列虚拟化。官方同时提供数值行高与批量 `rowNode.setRowHeight(height)` 后一次 `api.onRowHeightChanged()`，设行高属于 Community 能力。

来源：[AG Grid 36.2 — Row Height](https://www.ag-grid.com/archive/36.2.0/react-data-grid/row-height/#lazy-height-calculation)、[同页批量设高](https://www.ag-grid.com/archive/36.2.0/react-data-grid/row-height/#rownodesetrowheightheight-and-apionrowheightchanged)。

**本机补充：** 安装包 `ag-grid-community/dist/package/main.esm.mjs` 的 ClientSideRowModel.setRowTopAndRowIndex 在 `allowEstimate` 成立时先写默认估计值；`_getRowHeightForNode` 此时不执行 getRowHeight。故不能仅提供一个准确的 getRowHeight 回调，就宣称所有未渲染行已得到准确位置。推荐接入应通过公开节点 API 将当前已知行的高度实际写入模型，并在揭示前一次重排；内容变化只更新受影响节点。不得以关闭行虚拟化规避。

### E12. AG Grid 36.2 的自动列宽与动画不构成首次稳定保证

**官方结论：** fitCellContents 基于渲染内容；快速反复 sizeColumnsToFit 可造成滚动条闪烁，官方建议合适场景用列 flex。空数据时的类型推断可能使适配异步执行，可通过 cellDataType=false 改变该特定路径。

来源：[AG Grid 36.2 — Column Sizing](https://www.ag-grid.com/archive/36.2.0/react-data-grid/column-sizing/)。

**本机核对与推论：** 本机类型含 autoSizeStrategy、continuous、shouldAutoSizeColumns 与 animateColumnResizing；无需为这些选项升级。它们并不证明所有字体、换行和控件已完成准备；仅开列宽动画仍会连续改变换行。现有问题还有项目自定义 fitGridColumns/BoundedTable 的调度，不能只改官方选项。

### E13. 预计算也必须控制布局成本

**官方结论：** 几何属性变更触发布局，DOM 规模与复杂度影响成本；应批量读取布局信息再批量写样式，避免读写交替造成强制布局。

来源：[web.dev — Avoid large, complex layouts and layout thrashing](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)。

**本项目推论：** 使用受控大小的测量区、复用测量结果、批次处理；不为每个单元格各建一个立即读写的 Effect，也不复制整份大表 DOM。

## 整合后的推荐方案

**推荐选择：统一尺寸输入与计算顺序，在首次显示前提交完整布局；用缓存、增量更新和虚拟化控制成本，再给状态变化添加轻量动效。** 这是结合官方机制与本项目约束的设计判断，尚未实测收益，不是厂商提供的一键配置。

| 路线 | 结果与取舍 | 决定 |
| --- | --- | --- |
| 只恢复宽高动画 | 用户仍看见多轮重排，动画期间持续换行 | 不采用 |
| 所有表固定窄行并截断 | 容易稳定，但损失完整长文本和已确认体验 | 不采用 |
| 统一尺寸准备、缓存、一次显示及局部更新 | 保留完整内容，处理首屏和滚动；需验证测量成本 | 推荐 |

### 1. 先统一真正决定几何的基础样式

字体、四档字号、行距、上下留白、边框和控件高度从同一组 token 推导。基础行高必须容纳本行实际控件，而非全站硬写一个36px。例如现有 ledger 原生输入32px与上下留白组合，会把36px基准继续撑高；遮住首屏不能代替解决这种矛盾。

保留页面各自适合的高度：主工作表填满工作区，短表与卡片按其任务排布。表区外框和滚动条占位先稳定，避免纵向滚动条出现又缩小可用宽度，触发第二轮换行。

### 2. 列宽只由一个入口决定，先定宽再算高

日期、编号、金额、状态与操作列按其内容和控件需要确定合理宽度；长文本列采用有边界的可伸展宽度。复用现有纯函数 `tableWidths`，输入最终格式化文本、容器可用宽度、字体及业务最小宽，避免从已经被拉伸到100%的控件反推其“自然宽度”。AG Grid 与原生 table 使用同一份尺寸计划，分别通过列宽 API 和 colgroup 接入。

同一张表不能同时由 flex、页面 fit、字体回调等多个入口写列宽。窗口尺寸、字号、列结构真正改变时才重建宽度计划；普通刷新、排序、筛选沿用当前宽度。用户手调和编辑中的列宽优先，不因后台重读被重置。隐藏的保留页宽度为0时不测量、不覆盖有效缓存。

### 3. 完整长文本按最终宽度获得真实高度

短文本和标准控件走已验证的基础高度；仅对影响换行的内容进行精确测量。使用复用的、有真实布局宽度但不可见且不可交互的测量区，沿用实际单元格的 CSS 和显示结构，由浏览器处理中文/英文断行、标签与输入框；不新写字符数估行算法。

按“显示内容/控件结构＋最终列宽＋字体版本/字重＋字号＋样式版本”缓存。重复文本复用结果，批量读再批量写；大批量准备分批让出主线程，测量区 DOM 保持有界，不渲染一整份隐藏 AG Grid。

对当前已知数据集，生成准确的行高表并通过公开 API 实际写入 AG 行模型，再一次重排行位置；相应列不再让 lazy autoHeight 竞争改高。表头与分组表头也按最终宽度准备。原生表格沿用同一顺序和字体条件，复杂合并表按原结构测量。未来未加载的数据不能预知；数据到达后先准备再发布该批内容，不能把估计冒充准确。

这部分是实施时的关键性能验证点：完整长文本、虚拟化与全程稳定不能靠零成本估计同时保证。若实际数据使准备明显变慢，应优化测量复用与批次，不能悄悄改成截断或全量 DOM。

### 4. 数据与字体并行准备，按模块一次显示

顺序明确为：真实容器宽度与稳定滚动条空间 → 本次所需字体 → 列宽 → 表头及行高 → 应用布局 → 显示该模块。数据请求与字体准备尽可能并行；不要求整页所有卡片等最慢的一张表。导航、页头和工具条立即可见。

保留 MiSans 官方分片与现有字重，只提前发现关键片段，按当前参与测量的实际文本调用字体加载；不等待全部字库。缓存已就绪时直接使用。字体失败/加载异常时采用可读回退字体，并固定本次已显示内容的字体选择，迟到字体在下一次安全布局发布时再使用，避免边读边换字。具体等待边界须按冷缓存实测制定，不能无限等字体。

首次没有有效内容时，模块显示与最终表区外框一致的安静占位；准备很快则直接显示。正常 ready 必须来自当前布局版本的真实依赖和尺寸应用状态；固定 timeout、两次 rAF 或某个 firstDataRendered 事件不能单独当完成条件。等待和错误有明确出口。

### 5. 返回与更新复用现有画面，避免重新加载式闪烁

已加载页面返回时直接展示缓存布局和数据，后台重读使用局部状态提示。同业务范围刷新保留当前表格，按稳定行 ID 更新，只对变动内容失效缓存、修改必要行高；宽度保持。保护焦点、草稿、选择和阅读锚点。

项目/账号改变时按现有归属规则隐藏旧数据与编辑入口，在稳定表框内准备新范围内容。连续切换或调字号时仅最新一轮准备可以发布结果，迟到回调不能把旧尺寸覆盖回来。

### 6. 全站动效按场景统一

以下时长是项目初始调试参数，并非行业统一最优值；准备结束立即发布，不为播放动效延长等待。

| 场景 | 推荐体验 |
| --- | --- |
| 首次进入新模块 | 稳定表框先出现；内容就绪后约120–160ms轻淡入，不缩放、不滑动、不动画改宽高 |
| 返回已加载页面 | 直接显示，不重复淡入或骨架 |
| 同范围刷新/筛选/排序 | 保留画面，局部处理中提示；不整表消失重现，不飞行换位 |
| 实际值更新 | 必要时短暂弱背景提示，仅作用于变动单元格 |
| 用户拖动排序 | 拖动对象跟随，邻行约140–180ms短让位；同一行只保留一个可中断动画 |
| 用户改变窗口/字号 | 应用一次一致的新布局；保留阅读锚点，避免多轮回弹 |
| reduced-motion | 静态等待与状态反馈，关闭非必要动效 |

统计卡片、图表和弹窗内表格沿用首次显示/更新策略及稳定外框；保留现有弹窗交互，不扩大为全站所有组件重设计。骨架是否延迟出现以真实加载分布调试，不能人为设最低播放时间。

### 7. 落地范围与验收

以当前 React 工作树为范围：梳理所有主表、子视图、弹窗表格、原生/合并表及相关统计区，接入共享准备与反馈规则。主要复用 `grid.ts`、`table-widths.ts`、`bounded-table.tsx`、字号与主题样式；删除被取代的重复尺寸写入路径，保留必要业务渲染差异。保留现有 AG Grid 与 HTML table，不引入新的表格库、状态库、Worker 或 SSR。

实施建议先完成共享入口与一张有代表性的复杂表的真实性能证明，再把同一机制覆盖所有消费者；这是同一次全站交付中的内部验证顺序，不是另开预览或只修一页交差。原8065和原试用数据继续复用。

验收同时要求：

- 首次可见尺寸即已确定；同一输入没有默认宽高随后纠正，滚动进入已知新行不再因为估计替换而跳位。
- 冷/暖字体、四档字号、不同容器宽度、长文本及控件混排完整，无裁切、无旧项目残留；刷新和连续编辑不丢焦点/草稿/锚点。
- 分别记录数据到达、字体就绪、几何准备、正文可操作时间和主线程长任务；与同一8065数据和环境的基线对照。稳定不能靠延长隐藏时间换取，不能只看CLS。
- 所有表格消费者有覆盖清单和实际浏览器验证；对内容变化、字号变化、字体迟到与异步取消保留必要回归检查。

本轮仅形成研究与推荐方案，未修改产品源码、更新8065、启动服务或写业务数据；上述效果与性能尚未通过实施验收，不能作为已达成结果。

## 后续验证应回答的最少问题

- 首次可见的一帧是否已经是最终列宽、表头和当前可见行高；同节点是否仍发生“默认尺寸 → 计算尺寸”的连锁修正？
- 冷字体、暖字体、不同字号和窄容器下，正文可读可操作的实际时间是多少？把表格可见时间与尺寸准备耗时分别记录，避免“隐藏久一点所以稳定”掩盖变慢。
- 长文本、金额、标签、输入框混排和滚动新行是否完整；横滚是否引起纵向突跳；分页/切页返回是否保持锚点？
- 后台重读和连续编辑是否保住草稿、焦点、选择与滚动；换项目是否没有旧项目数据/入口残留？
- 普通与 reduced-motion 下是否都无默认几何闪现，且等待、空、错误准确区分？

建议验收目标是“用户无需目睹默认几何纠正、正常刷新不打断编辑，并在相同条件下保持或改善实际可操作时间”。本研究没有实测延迟、改善百分比，也没有证据保证某个统一毫秒预算能覆盖全部表格。数值目标应在现有 8065 的同输入基线上制定，保留数据与现行唯一试用副本；研究本身不授权启动任何验证、修改或新预览。
