## 一、策略转向：从「建档收敛」到「全自动建档」

### 1.1 转向内容

| 场景 | 现在 | 改为 |
|---|---|---|
| **活跃业务**（收发结存 / 库存单据）遇陌生仓库 | **报错**，要求先手工同步项目 | **自动跑一次仓库同步 → 扶正 → 重跑导入** |
| **欠款类**（付款通知书 / 付款计划）遇陌生项目 | 自动建档，`name = 全名` | 自动建档，`name = 未建仓-序号`（**占位名**） |

### 1.2 ⚠️ 转向必须带上的"安全带"

当初收紧建档，是因为踩过坑（全量建档会引入历史老项目脏数据）。**放开之前，先把那个坑堵上**：

| 当年的坑 | 现在的堵法 |
|---|---|
| 全量建档把 i8 里**历史老项目**也建成行，污染统计 | **只对"当前常用项目列表"里的项目建档**；老项目靠数据导入被动建档，且标为"归档" |
| 流水/材料数据各自建档，**同一项目建出多行** | 建档前先走**三维匹配**（phid → 仓库名 → 全名）+ 别名兜底 |
| 判类靠名字猜，**改名即崩** | 识别关键字**配置化**（见 §三），不硬编码 |
| 建了行但没数据，**统计口径被稀释** | 占位行必须有 `is_placeholder` 语义（用 `未建仓-` 前缀判定），**默认不计入在建统计** |

## 二、6 项决策结论（2026-09-11 全部按建议拍板）

> 以下**每一条均为已拍板结论**；原始讨论过程（"我的建议 / 理由 / 是否采纳"）已收敛为结论 + 关键规则，口径零删减。

### 决策 1 · ✅ 三类项目自动判（双轨 + 人工可覆盖）

| 判据 | 规则 | 强度 |
|---|---|---|
| **主判据** | **命名约定**：项目全名含「小微」→ 小微壳 | 命名约定已在业务中验证可用 |
| **推导判据** | 仓库列表里，某仓库的「所属项目全名」= 壳全名 → 该仓库是**具体小微**；= 普通项目全名 → 该仓库是**普通项目** | 从 i8 两接口自动推导 |
| **兜底** | 某全名挂 ≥2 个仓库、且未含「小微」→ **提示用户确认是否为壳** | 防命名约定被打破 |
| **人工覆盖** | 提供「标记为壳 / 取消壳」开关，手工判断优先 | 兜底中的兜底 |

**同时要求：** 把「小微」这个关键字**做成可配置项**（像剔除规则那样），**不硬编码**——i8 一旦改名，改配置即可，不用改代码。

### 决策 2 · ✅ 普通项目 ↔ 仓库：**1 : 1**（2026-09-12 按业务事实收紧）

> **业务事实（用户口径）：一个项目不可能有两个仓库。** ⇒ 普通项目 ↔ 仓库 = **1 : 1**。

建模仍按「**一个仓库 = 一行档案**」，但**唯一约束设在「仓库名」上、不设在全名上** —— 因为**小微壳结构**会让同一全名合法地对上多行（1 个壳 + N 个具体小微，每个具体小微各有一个仓库）。这样既不会因唯一约束冲突而建档失败，又与"仓库名 = 唯一标识"的口径自洽。

> **推论（重要，决定归属判定的形态）：** 一个全名对应多条档案，**唯一的原因只能是"它是壳"**。
> ⇒ 普通项目全名**永远唯一命中**、归属天生确定、**永不出现「待指定」**；
> ⇒ 「某全名挂 ≥2 个仓库、又不含『小微』」只可能是**名字没带"小微"的壳** —— 正是决策 1 那条兜底弹窗要处理的情形。

### 决策 3 · ✅ 小微识别关键词存哪

从全局规则 `small_map` **迁到「项目行」的字段**（如 `match_keywords`，`|词1|词2|` 格式，复用 aliases 的存储模式）。
理由：关键词本是**具体小微的属性**；迁到行上后"新增小微 = 建行时顺手录词"，不必再维护一张全局映射表。

### 决策 4 · ✅ 关键词能否重复

**允许**；命中多个时**弹出让用户选**（复用"抓仓库多结果"的交互），并把选中的词**去重追加**到该小微名下。
理由：禁止重复会让人工配置变难；弹窗选择既安全又不阻塞。

### 决策 5 · ✅ 数据模型加 2 个字段

| 字段 | 用途 | 理由 |
|---|---|---|
| `project_type`（normal / shell / small） | 显式类型 | 靠 `'小微' in name` 猜类型会**改名即崩**；显式字段可审计、可筛选 |
| `parent_shell_id` | 具体小微 → 壳 | 靠"全名相同"隐式关联，一对多时容易错 |

> 占位行**不另加字段**——靠 `name LIKE '未建仓-%'` 判定即可（省一个字段）。

### 决策 6 · ✅ 尾码剥离统一取最宽规则

剥离规则的严格程度在三处不一致（从"完全不剥"到"仅大写 ≥3 字母"不等）。

取**最宽的一套 `[A-Za-z]{2,}\d+`**（能涵盖其余全部情形），抽成公共函数 `strip_trailing_code()`，**三处共用**。
另：**付款通知书导出侧也要剥**（这是过去最不一致的一处）。

## 三、核心设计：三条链路

### 链路 A · 付款侧自动建档

```
抓付款通知书（含「付款项目」全名）
   │
   ├─ ① 全名是否已在档案中？
   │     是 → 归集（结束）
   │     否 → ②
   │
   ├─ ② 全名是否命中某个「壳」（project_type = shell）？
   │     是 → 走链路 C（小微拆解）
   │     否 → ③
   │
   └─ ③ 启动建档
         a. 抓 phid（常用项目列表）
             ├─ 抓到 → 继续
             └─ 未抓到 → 提示「请将该未建档项目加入 i8 常用项目列表」，点继续后重试
         b. 抓仓库信息（仓库列表按全名反查）
             ├─ 抓到 1 个 → 建档完成（真实仓库名）
             ├─ 抓到多个 → **列出让用户选**，只建选中的那个
             └─ 未抓到 → 建档，name = **未建仓-序号**（占位）
```

**关键点：**

- phid 抓不到**保留人工环节**（有意为之：项目已在走付款却没进常用列表，属操作遗漏，需要被提醒到）
- 占位行的 `full_name` **仍写全名**——这是后面扶正的"钥匙"
- 占位行 `project_type` 按判定规则填；`status` 填 **在建**

### 链路 B · 材料侧自动扶正

```
导入材料报表（收发结存 / 库存单据明细）
   │
   ├─ 遇陌生仓库（不在档案里）
   │     │
   │     ├─ ① 「陌生仓库」事实留痕（见 §五）→ 看板瓦片「占位行待扶正」＋ 抓取回执里列出
   │     ├─ ② 自动跑一次「抓仓库名单」同步
   │     ├─ ③ 用**全名**回查占位行（占位行的 full_name 就是全名）
   │     │       ├─ 命中 1 条 → 扶正：name 由 未建仓-01 → 真实仓库名
   │     │       ├─ 命中多条 → **弹窗让用户指认**（小微一对多的情形）
   │     │       └─ 未命中   → 新建行（真实仓库名）
   │     └─ ④ 无需"重跑"步骤 —— 导入过程中即同步扶正（见下方"两处追认"）
   │
   └─ 无陌生仓库 → 正常导入
```

**为什么两支材料报表都覆盖：**
- **库存单据明细**：表里有「项目名称」（全名）列，可直接定位
- **收发结存**：只有仓库列、没有全名列 → 只能靠"出现陌生仓库"触发
- 因此**统一以"陌生仓库"为触发条件**，两种情况都能走到

> **⚠️ 两处形态追认（2026-09-17 · 用户批准「按推荐」）** —— 把「文档写的」与「实际做的」对齐，**不改口径**：
> - **① 的形态** = **看板瓦片「占位行待扶正」** ＋ **抓取回执里列出**（⛔ **不是**独立的"告警记录"）。
>   依据：`demo/` 原型 **2026-09-14 看板改造**已撤掉独立告警卡、并入该瓦片（两者同一数据源：
>   `PJs.filter(p => p.name.startsWith('未建仓-'))`）⇒ **原型即交互规格**（§0.1 权威优先级）。
> - **④ 无"重跑"这一步**：实现为**导入过程中同步扶正** —— `recovery.recover_unknown_warehouses` 在抓取链路上
>   直接调用，数据落库前已处理完 ⇒ **不存在"先落库、再回头改"**；降级时由人**再抓一次**
>   （回执原文："数据已照常入库，可稍后重抓一次"）。
>
> ⚠️ **③「命中多条 ⇒ 弹窗让用户指认」仍是待做**：当前实现只把该情形**报出来**（进 `unresolved`、带原因），
> **选择入口待补** —— 形式照原型 `promote` 弹窗（「扶正占位行」里那个"选真实仓库名"的下拉）。

### 链路 C · 小微两层

```
【壳已建档】
  用单据名称与「该壳下各具体小微的关键词」匹配
    ├─ 命中 1 个小微 → 归集到它，关键词去重追加
    ├─ 命中多个       → 弹窗让用户选（选中后关键词追加）
    └─ 未命中         → 弹窗列表：
                         ① 目前在建的具体小微（每个右侧必填框，内容必须出现在单据名中）
                         ② 最后一行「该项目属于新小微」
                        ├─ 选已有小微 + 填词 → 词追加 → 结束
                        └─ 选「新小微」    → 抓仓库信息 → 建小微行 + 录关键词

【壳未建档】
  先建壳（走链路 A 的 ③）→ 抓仓库信息 → 请用户录入关键词 → 建具体小微行
```

**⚠️ 必须保留的铁律（§9.8-5/6）：** 若「付款项目」在壳映射里查不到、但库里已有某个具体小微的全名 = 该全名 → **不得用全名反查命中**，应判定为"壳未建档"，走未建档分支。否则会把钱记到**错误的小微**头上。

> **技术落点：** 所有落到具体小微的写操作，**一律按 id 传参**，前端回传 id 而非名字。

## 四、7 项技术项的落地方式

| # | 技术项 | 落地做法 |
|---|---|---|
| 1 | **禁止修改仓库名** | 前端不提供改名入口；后端 `rename` 接口**限定只允许系统扶正调用**（占位行 → 真实名），人工改名一律拒绝 |
| 2 | **统一尾码剥离** | 抽 `strip_trailing_code()` 公共函数（规则取 `[A-Za-z]{2,}\d+`），**导出 / 仓库同步 / 项目同步 三处共用** |
| 3 | **全名人工修改** | 提供前端入口 + **留痕**（改前值、改后人、时间） |
| 4 | **定位一律走 id** | 归集、加关键词、扶正等写操作全部接 id；名字仅用于"读时匹配" |
| 5 | **占位名序号生成** | `未建仓-%02d`；**事务内**取号（`SELECT MAX` + 行锁 或 唯一索引 + 重试），防两人并发撞号 |
| 6 | **抓仓库多结果** | 接口返回列表，前端弹窗选择，**只建选中的** |
| 7 | **扶正逻辑** | 见链路 B |

## 五、两条业务事实的监测与兜底（安全带）

这两条**不是设计禁令，是"业务事实"** —— 它们是整个设计的地基，之所以写下来，是因为**被打破时系统必须能察觉**：

| 业务事实 | 含义 | 监测点 | 触发后动作 |
|---|---|---|---|
| 1 | **付款通知书一定早于仓库** | 材料报表导入时**出现陌生仓库** | ① 正常扶正（链路 B）② **记一条告警**："有项目绕过了付款流程"——说明业务事实被打破了一次，供事后复盘 |
| 2 | **上线后补导近半年** | 上线初始化时：**档案行数 vs i8 仓库数** 对不上 | 提示补导缺失月份 |

> 业务事实 1 的监测点**不能省**——它是"整个自动建档是否还成立"的天然哨兵。
> ⚠️ **术语约定**：「铁律」在本项目**专指 §9.8 的 7 条业务铁律**；本节讲的是业务事实，两者不要混用。
> 原第 2 条「不存在整月不付款（抓取条数为 0 即告警）」**已移除**（2026-09-12 用户口径：那只是随口一提，不需要该监控）。

## 六、分阶段实施计划

| 阶段 | 内容 | 交付物 | 验收标准 |
|---|---|---|---|
| **阶段 0 · 口径冻结** | 拍板本文 §二 的 6 项；确认数据模型变更 | 决策记录 | 6 项全部有结论 |
| **阶段 1 · 抓取与判定** | ① i8 抓取层（常用项目列表 / 仓库列表，纯 HTTP）② `strip_trailing_code()` 公共函数 ③ **三类项目自动判定器** ④ 2 个新字段迁移 | `i8/exports` 抓取模块 + 判定器 + Alembic 迁移 | 抓两次结果一致；三类项目判定与人工核对**100% 吻合**；尾码三处输出一致 |
| **阶段 2 · 占位建档（链路 A）** | 付款通知书导入遇陌生项目 → 抓 phid → 抓仓库 → 建档/占位 | 导入器改造 + 占位序号生成 | 新项目自动出现档案行；多仓库时能选择；占位行 full_name 正确 |
| **阶段 3 · 扶正闭环（链路 B）** | 陌生仓库 → 同步 → 扶正 → 重跑；两条材料报表都覆盖 | 导入器改造 + 扶正服务 | 造一个"先有仓库后建档"的场景，能自动扶正并重跑成功；告警有记录 |
| **阶段 4 · 小微两层（链路 C）** | 关键词匹配归集 + 未命中弹窗 + 新小微建档；**关键词迁到项目行** | 交互 + 服务 | 壳/具体小微/新小微三条分支各跑通一次；**全名反查陷阱有测试覆盖** |
| **阶段 5 · 监测与回归** | 两条业务事实监测点；全量回归 | 告警 + 回归报告 | 业务事实 1/2 各能触发一次；`pytest` 全绿 |
| **阶段 6 · 交互引导层** | 建档向导 UI 稿（含多结果选择、新小微录入、全名修改） | UI 稿 | 用户确认 |

**依赖关系：** 阶段 1 → 2 → 3 → 4 严格串行（后者依赖前者的抓取与判定能力）；阶段 0 是所有阶段的前提。

## 八、风险与回退

| 风险 | 影响 | 应对 |
|---|---|---|
| 自动建档引入脏数据（当年收紧的原因） | 统计被污染 | 只对常用列表建档；占位行默认不计入在建统计；保留"归档/软删"清理通道 |
| 命名约定（含"小微"）被 i8 改名打破 | 判类错误 | 关键字配置化 + 兜底提示 + 人工覆盖开关 |

| 占位序号并发撞号（两人同时导入） | 唯一约束冲突 | 事务内取号 + 唯一索引 + 失败重试 |
| 扶正后重跑导入失败 | 导入中断 | 重跑需**幂等**（已有 `delete_auto_rows` + UPSERT 机制） |
| 回退 | — | 阶段 2/3 功能提供**开关**，异常时一键回到"遇陌生项目报错"的旧行为 |

| # | 问题 | 用户口径 | 对设计的影响 |
|---|---|---|---|
| 1 | 一个壳最多挂几个具体小微？**能否换壳**？ | **理论上无限**；实际约 **2-3 个/年**，且**一年一个壳** | 规模小 → 弹窗选择完全够用；**不支持换壳**（会破坏历史归属） |
| 2 | 壳不存在时，具体小微**能否单独存在**？ | **不能** | 建档顺序**强制：先壳后小微** |
| 3 | 重复项目**怎么合并**？ | **基本不会出现**；即使出现也**一定在项目初期、还没有数据时** | **不单独做"合并"功能**；改为初始阶段**行删除 + 重建**（无数据，零风险） |
| 4 | 多仓库提示：**逐次弹窗**还是**汇总列表**？ | **弹窗**，且基本不会出现 | 走逐次弹窗；不做"待确认列表"页面 |

> **规模感总结（重要）：** 壳 **一年一个**、具体小微 **一年两三个** → 这套建档流程的实际人工介入量**极低**。因此设计重心应放在 **"不出错"**（防误归集、防脏数据），而不是 **"少点击"**。所有"为省一次点击而增加风险"的简化，一律否决。
