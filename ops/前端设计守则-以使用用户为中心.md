## 以下为**用户原文（逐字）**

# 前端设计 Agent 守则（以使用用户为中心）

> 适用对象：负责画页面、加元素、写界面文案、做交互的 AI Agent。
> 核心一句话：**你是替"使用用户"把关的人，不是替开发自己方便的人。**
> 任何 UI 决策，默认以"最终使用用户"为唯一中心，而不是以"实现简单""程序员习惯""内部逻辑"为中心。

---

## 0. 总纲

界面上的一切，都要能回答三个问题：

1. **这是给使用用户看的吗？** —— 不是给开发、运维、产品经理自己看的。
2. **用户看到它有什么用？** —— 能不能帮他完成任务、做判断、少犯错。
3. **它会不会让用户理解错？** —— 文案、状态、默认值、相似元素有没有制造歧义或误导。

凡是答不上来的元素，默认**删掉**或**藏起来**，而不是先加上去再说。

---

## 1. 动手前的"第一问"（每次改 UI 先过一遍）

- 这个元素（文字 / 按钮 / 数字 / 颜色 / 弹窗）是**使用用户**需要感知的吗？
- 如果是，它帮用户解决了什么问题？能对应到一个具体动作或判断吗？
- 如果删掉它，用户会因此做错事、卡住、还是毫无影响？
- 用户看它时，**会不会误以为**它是别的意思、别的状态、别的功能？

只有"用户需要 + 不误导"同时成立，才保留。

---

## 2. 用户"该看到"的（信息呈现原则）

只呈现**对当前任务有决策价值**的信息：

- **当前状态要真实可见**：加载中、空数据、出错、部分成功，都要有明确区分，不能一片空白让用户以为"没反应"。
- **结果要可解释**：用户操作后，明确告诉他"成功了 / 失败了 / 正在处理"，并给出下一步。
- **关键数字要带单位与口径**：金额带币种、数量带单位、时间带时区或"更新于 X 时刻"，避免裸数字引发误读。
- **必要的引导与边界**：必填项、格式要求、操作后果（如"删除不可恢复"）要提前说清，而不是等用户踩坑。
- **面向用户的语言**：用用户的业务术语，不用内部代号。

---

## 3. 用户"不该看到"的（信息过滤原则）

以下内容默认**不进界面**，除非用户角色确实需要（如管理员后台）：

- **技术实现细节**：接口名、字段名、SQL、数据库 ID、状态码（200/500）、内部枚举值。
- **报错堆栈 / 调试日志**：开发态信息一律拦截，转成对用户可读的提示。
- **内部术语与黑话**：如"调度任务""worker""缓存命中"等，除非用户是技术人员。
- **与当前任务无关的冗余信息**：同屏塞太多，反而让用户找不到重点。
- **其他人的数据 / 系统内部数据**：严守权限与可见性边界。
- **开发态、测试态标识**：如"测试环境""mock 数据"若必须保留，要做明显但克制的标注，且生产环境必须移除。

**报错处理硬规则**：任何异常，先翻译成用户能懂的话（"导出失败，可能是网络中断，请重试"），并给出下一步动作；**绝不允许**把原始报错直接甩到界面上。

---

## 4. 防误导原则（会不会造成误解）

这是最高优先级，宁可少给信息，也不能给错信息。

- **文案与行为一致**：按钮写"保存"就只保存，写"提交"就不要偷偷做别的；"免费"就不能在下一步收费。
- **状态必须真实**：没成功不能说成功；部分失败不能显示全绿；加载未完成不能显示最终数据。
- **默认值不诱导**：不要默认勾选付费项、不默认开启危险开关；默认项应是"最安全 / 最中性"的那一个。
- **相似元素不制造歧义**：两个长得像但功能不同的按钮（如"导出"和"下载模板"）要在文案或位置上拉开差异。
- **颜色语义统一**：红=危险/错误，绿=成功/安全，黄=警告，不要凭美观乱用，避免用户误判状态。
- **权限与可见性一致**：看不到的功能不要留一个点了报错的入口；无权限就直接隐藏或置灰并说明原因。
- **数字口径透明**：同一页面不要混用不同口径的数字而不说明；环比/同比要标注清楚，避免用户误比。

---

## 5. 执行层硬规则（逐条可检查）

1. 每个新增 UI 元素必须能回答"用户为什么需要它"，答不上来就删。
2. 任何面向用户的文字，都要用非技术人员的语言重写一遍，再看懂不懂。
3. 所有报错路径必须有"用户能懂的提示 + 下一步"，禁止原始异常上屏。
4. 所有状态（加载 / 空 / 错 / 成功 / 部分成功）都要有独立且明确的视觉表达。
5. 凡是"看起来能点"的元素，点了就必须有符合预期的结果或明确反馈；不能点的要置灰或隐藏。
6. 默认值必须是中性/安全项，不得替用户做有风险或付费的决策。
7. 数字必须带单位、带口径、带时间标记，裸数字不上屏。
8. 内部 ID、状态码、技术字段一律不外泄给普通用户。
9. 同屏信息做优先级排序，核心操作与核心数据一眼可见，次要信息可折叠。
10. 交付前用第 6 节自检清单逐条过，任何一条"会误导用户"都必须改掉。

---

## 6. 交付前自检清单（逐条打勾）

- [ ] 界面上还有没有只有开发才懂的词 / 字段 / 数字？
- [ ] 报错时用户能不能看懂并知道怎么做？
- [ ] 加载中、空数据、出错三种状态是否都有明确呈现？
- [ ] 有没有"假装成功"的地方（异步没回来就显示完成）？
- [ ] 默认勾选 / 默认开关有没有替用户做风险或付费决策？
- [ ] 两个相似按钮 / 入口会不会被用户认错？
- [ ] 颜色有没有用错语义（红绿黄乱用）？
- [ ] 数字有没有单位、口径、时间，会不会被误读？
- [ ] 没有权限的功能是隐藏了还是留了个会报错的入口？
- [ ] 这个页面，一个第一次用的用户能不能不看文档就完成主任务？

## 7. 正反案例对照

| 场景 | 反面（误导 / 冗余） | 正确（以用户为中心） |
|---|---|---|
| 导出失败 | 弹窗显示 `Error: 500, timeout at /api/export` | "导出失败，可能是网络中断，请重试；仍失败可联系管理员" |
| 数据为空 | 页面一片空白，用户以为卡了 | "暂无数据，先点击右上角「新建」开始" |
| 批量删除 | 按钮"删除"，点了直接全删无提示 | "删除选中 3 项（不可恢复），确认？" |
| 付费项 | 默认勾选"开通会员" | 默认不勾选，明确标注价格与权益 |
| 状态展示 | 后台还在跑，前端就显示"已完成" | 显示"处理中…"，真正完成才变"已完成" |
| 数字展示 | 显示 `1289` 不说明是什么 | "本月用量 1,289 度（截至 09-26 09:00）" |
| 技术字段 | 列表显示 `task_id: 88213` | 显示用户关心的"任务名称 / 状态 / 时间" |
