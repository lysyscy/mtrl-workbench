# 前端设计守则 · **以使用用户为中心**（`v2` 标准形态 · `[用户·2026-09-26]` 立）

> **读者**：任何要画页面 / 加元素 / 写界面文案 / 做交互的 Agent（含我）与接手的人。
> **回答**：界面上**该有什么**、**不该有什么**、**怎么判断**、**谁在守它**。
> **何时读**：动前端**之前**（改文案 / 加控件 / 改版式都算）；**审计前端时逐条打勾**。
> **状态**：⛔ **本件 = 唯一主人**（别处只许引用，⚠️ 仓库里此前被引到的《前端设计规则》**从未存档**、已作废）。

> 加的是**编号 · 字段 · 判据挂钩 · 索引 · 变更记录** —— 让"照着做"和"查有没有做到"都有落点。

1. **动手前**：过 §1「第一问」＋ §3「不该看到的」——**答不上来的元素默认删掉或藏起来**；

## §1 动手前的「第一问」（每次改 UI 先过一遍）

> 用户原话：**只有"用户需要 + 不误导"同时成立，才保留。**

| 编号 | 规则 | 为什么 · 反例 | 判据 |
|---|---|---|---|
| §1.1 | 【必需】这个元素（文字 / 按钮 / 数字 / 颜色 / 弹窗）是**使用用户**需要感知的吗？ | 答"不"就该走 §3（藏起来或删掉）。反例：把内部字段名当列名铺给人看 | `人眼 · 未挂`（§3 那半有判据） |
| §1.2 | 【必需】它帮用户解决了什么问题？能对应到一个具体动作或判断吗？ | 答不上来 = 装饰。反例：一排"看起来很重要"但没人会点的按钮 | `人眼 · 未挂` |
| §1.3 | 【必需】如果删掉它，用户会因此做错事、卡住、还是毫无影响？ | "毫无影响"⇒ 删 | `人眼 · 未挂` |
| §1.4 | 【必需】用户看它时，**会不会误以为**它是别的意思、别的状态、别的功能？ | 见 §4（防误导是最高优先级） | 见 §4 各条 |

## §2 用户「该看到」的（信息呈现原则）

> 用户原话：**只呈现对当前任务有决策价值的信息。**

| 编号 | 规则 | 为什么 · 反例 | 判据 |
|---|---|---|---|
| §2.1 | 【必需】当前状态**真实可见**：加载中 / 空数据 / 出错 / 部分成功都要有明确区分。 | 一片空白 ⇒ 用户以为"没反应"。反例：面板搜不到时留空 | `test_imp_shell`（③ 空态人话）· 真机段 ⑳′ |
| §2.2 | 【必需】结果**可解释**：操作后明确告诉"成功了 / 失败了 / 正在处理"，并给出下一步。 | 用户得自己猜发生了什么 | `test_imp_shell`（回执卡）· 真机段 ⑳′ |
| §2.3 | 【必需】关键数字**带单位与口径**（币种 / 单位 / "更新于 X 时刻"）。 | 裸数字必被误读 | `人眼 · 未挂`（部分：`lgMd` 渲染口径见 §2.7） |
| §2.4 | 【必需】必要的**引导与边界**：必填项 / 格式要求 / 操作后果（如"删除不可恢复"）要**提前**说清。 | 等用户踩坑才算坏。反例：「截止核算月」不写 `YYYY-MM` | `test_imp_shell`（§5.5 同款：格式要求贴控件） |
| §2.5 | 【必需】**面向用户的语言**：用业务术语，不用内部代号。 | 见 §3.1。反例：界面写 `cutoff_ym` / `project key` | `test_imp_shell`（结果卡只画域自报的 `kpis`） |
| §2.6 | 【应当】能算出来的**别让人自己数**（总数 / 走没走完 / 差几行）。 | 用户数错 = 系统的错 | `人眼 · 未挂` |
| §2.7 | 【必需】**结论要贴在被说的那个对象上** —— 要标就标在那一行/那一格上，⛔ 别让人抬头去别处读一句说明再自己对上号。`[补充·2026-09-26]` | 用户报障原话：「**这些不会落库的行，要在行上直接标**，比如给一个浅色底，或者其他明确提示，**这才叫好的前端设计**，而不是还要**抬头去看文字说明**」。反例：卡片底下写"有 7 行不会写入"，表里 7 行**长得跟别的行一模一样**（用户得自己拿红框对） | `test_imp_shell::test_不会落库的行要在行上直接标`（域自报 `skipped` ＋ 壳标行 ＋ 行内文字标记 ＋ 图例）· 真机段 ③″（**卡片说的数 == 行上标出的数**）· 4 域 API 判据 `imp_contract.assert_skipped_contract` |

## §3 用户「不该看到」的（信息过滤原则）

> 用户原话：**以下内容默认不进界面，除非用户角色确实需要（如管理员后台）。**

| 编号 | 规则 | 为什么 · 反例 | 判据 |
|---|---|---|---|
| §3.1 | 【必需】技术实现细节（接口名 / 字段名 / SQL / 数据库 ID / 状态码 / 内部枚举值）不上屏。 | 反例：列表显示 `task_id: 88213`、回执铺一排 `undo_rows` | `test_imp_shell`（结果卡：原始键进「技术明细」折叠区）· ⛔ **通用文案扫查未挂**（`TAIL-105` 余项） |
| §3.2 | 【必需】报错堆栈 / 调试日志一律拦截，转成用户可读的提示。 | 反例：弹窗 `Error: 500, timeout at /api/export` | `人眼 · 未挂`（后端统一 `MustReportError` 是另一半） |
| §3.3 | 【必需】内部术语与黑话不入界面（"调度任务" / "worker" / "缓存命中"…）。 | 除非用户是技术人员 | `人眼 · 未挂` |
| §3.4 | 【应当】与当前任务无关的冗余信息不塞（同屏太多 = 找不到重点）。 | 与 §5.9 同源 | `人眼 · 未挂` |
| §3.5 | 【必需】其他人的数据 / 系统内部数据严守可见性边界。 | 权限问题，非审美问题 | 各域权限判据（`test_acc_*` 口径） |
| §3.6 | 【必需】开发态 / 测试态标识若必须保留，要**明显但克制**，且生产环境必须移除。 | 反例：生产库里留着 `__自检仓_*` 混进候选 | 真机段 ㉒（开发库卫生：自检残留报红） |
| §3.7 | 【必需】**报错处理硬规则**：任何异常先翻译成用户能懂的话（"导出失败，可能是网络中断，请重试"）＋ 给出下一步；**绝不允许**原始报错直接甩上界面。 | 用户看不懂 = 等于没报 | `人眼 · 未挂`（后端 `MustReportError` 兜住一半） |

## §4 防误导原则（**最高优先级**）

> 用户原话：**宁可少给信息，也不能给错信息。**

| 编号 | 规则 | 为什么 · 反例 | 判据 |
|---|---|---|---|
| §4.1 | 【必需】文案与行为一致：写"保存"就只保存、写"提交"就别偷偷做别的。 | 反例：按钮叫「导出」实际改了数据 | `人眼 · 未挂` |
| §4.2 | 【必需】**状态必须真实**：没成功不能说成功；部分失败不能显示全绿；加载未完成不显示最终数据。 | 反例：干跑（`dry_run`）还写"导入完成"；给"不落库的行"标上会落库的样子 | `test_imp_m05_api`（预览零写库）· `test_imp_m06_api`（`cutoff_ym` 只取能落库的）· `test_imp_m04_api`（本域无「不落库」⇒ 不许给 `skipped`） |
| §4.3 | 【必需】默认值不诱导：不默认勾选付费项 / 不默认开危险开关；默认项 = **最安全 / 最中性**。 | 反例：默认勾选"开通会员" | 各域判据（写动作） |
| §4.4 | 【必需】相似元素不制造歧义：两个长得像但功能不同的按钮要在文案或位置上拉开。 | 反例：「导出」与「下载模板」并排同款 | `人眼 · 未挂` |
| §4.5 | 【必需】**颜色只承担语义**：红=危险/错误、绿=成功/安全、黄=警告 —— 不许凭美观乱用。 | 反例：绿底表示"被跳过"。⚠️ 同一状态**不许两套视觉语言**（换一类浮层/行就重造一套色） | 壳 CSS token 审查（`ui_parity` ＋ 无硬编码色值断言）· `.skiprow`/`.ntvoid` 同源（inset 竖条＋浅底） |
| §4.6 | 【必需】权限与可见性一致：看不到的功能不留"点了报错的入口"；无权限就隐藏或置灰**并说明原因**。 | 反例：灰按钮不给理由 | `test_imp_shell`（④ 置灰 ＋ 说明缺什么）· 守则 §5.5 同款 |
| §4.7 | 【必需】数字口径透明：同页不混用不同口径而不说明；环比/同比标注清楚。 | 反例：两个"合计"口径不同却并排 | ⭐ 本仓落地：同一数在两屏**用同一个词**（预览 `配上` == 回执 `配上并更新`）⇒ `test_imp_m11_api` |

## §5 执行层硬规则（逐条可检查）

> 用户原话（§5 前言）：**逐条可检查**。⚠️ 本节的第 N 条 = `§5.N`（代码里的引用按这个号）。

| 编号 | 规则 | 为什么 · 反例 | 判据 |
|---|---|---|---|
| §5.1 | 【必需】每个新增 UI 元素必须能回答"用户为什么需要它"，答不上来就删。 | = §1.2 | `人眼 · 未挂` |
| §5.2 | 【必需】任何面向用户的文字，都要用非技术人员的语言**重写一遍**再看懂不懂。 | = §2.5/§3.1 | `人眼 · 未挂`（`TAIL-105` 余项） |
| §5.3 | 【必需】所有报错路径必须有"用户能懂的提示 ＋ 下一步"，禁止原始异常上屏。 | = §3.7 | 后端 `MustReportError`（各域判据）· 壳侧 `人眼 · 未挂` |
| §5.4 | 【必需】所有状态（加载 / 空 / 错 / 成功 / 部分成功）都要有独立且明确的视觉表达。 | = §2.1 | `人眼 · 未挂` |
| §5.5 | 【必需】凡是"看起来能点"的元素，点了就必须有**符合预期**的结果或明确反馈；**不能点的要置灰或隐藏，并说明为什么**。 | 反例：灰按钮不写缺什么（用户只能猜）；点了没反应 | `test_imp_shell`（④ 置灰 ＋ 缺什么说清）· 真机段 ①″/③″ · `test_imp_shell`（提交期间 `busy` 挡重入） |
| §5.6 | 【必需】默认值必须是中性/安全项，不替用户做有风险或付费的决策。 | = §4.3 | 各域判据 |
| §5.7 | 【必需】数字必须带单位、带口径、带时间标记，裸数字不上屏。 | = §2.3 | `人眼 · 未挂` |
| §5.8 | 【必需】内部 ID / 状态码 / 技术字段一律不外泄给普通用户。 | = §3.1 | `test_imp_shell`（结果卡分工：人话 KPI ／ 原始键折叠） |
| §5.9 | 【必需】同屏信息做**优先级排序**：核心操作与核心数据一眼可见，次要信息**可折叠**。 | 反例：把技术键与业务指标混成一排 KPI（用户找不到重点）—— 正是 2026-09-26「落库结果可读性差」的病根 | `test_imp_shell::test_落库结果卡给的是人话_原始键名进技术明细`（`<details>` 折叠 ＋ 人话 KPI ＋ 一句话结果整行） |
| §5.10 | 【必需】交付前用 §6 自检清单逐条过，任何一条"会误导用户"都必须改掉。 | —— | 人眼（§6）＋ 各条判据 |

## §6 交付前自检清单（逐条打勾）

- [ ] 界面上还有没有只有开发才懂的词 / 字段 / 数字？（§3.1 §5.8）
- [ ] 报错时用户能不能看懂并知道怎么做？（§3.7 §5.3）
- [ ] 加载中、空数据、出错三种状态是否都有明确呈现？（§2.1 §5.4）
- [ ] 有没有"假装成功"的地方（异步没回来就显示完成 / 干跑说"完成"）？（§4.2）
- [ ] 默认勾选 / 默认开关有没有替用户做风险或付费决策？（§4.3 §5.6）
- [ ] 两个相似按钮 / 入口会不会被用户认错？（§4.4）
- [ ] 颜色有没有用错语义（红绿黄乱用 / 同一状态两套视觉语言）？（§4.5）
- [ ] 数字有没有单位、口径、时间，会不会被误读？（§2.3 §5.7）
- [ ] 没有权限的功能是隐藏了还是留了个会报错的入口？（§4.6 §5.5）
- [ ] 这个页面，一个第一次用的用户能不能不看文档就完成主任务？（§2 全节）
- [ ] ⭐ 凡是"说出了一个数/一个结论"的地方，**它的对象上有没有对应的标记**？（§2.7）

# 前端设计 Agent 守则（以使用用户为中心）

> 适用对象：负责画页面、加元素、写界面文案、做交互的 AI Agent。
> 核心一句话：**你是替"使用用户"把关的人，不是替开发自己方便的人。**
> 任何 UI 决策，默认以"最终使用用户"为唯一中心，而不是以"实现简单""程序员习惯""内部逻辑"为中心。

---

## 0. 总纲

界面上的一切，都要能回答三个问题：

1. **这是给使用用户看的吗？** —— 不是给开发、运维、产品经理自己看的。
2. **用户看到它有什么用？** —— 能不能帮他完成任务、做判断、少犯错。
3. **它会不会让用户理解错？** —— 文案、状态、默认值、相似元素有没有制造歧义或误导。

凡是答不上来的元素，默认**删掉**或**藏起来**，而不是先加上去再说。

---

## 1. 动手前的"第一问"（每次改 UI 先过一遍）

- 这个元素（文字 / 按钮 / 数字 / 颜色 / 弹窗）是**使用用户**需要感知的吗？
- 如果是，它帮用户解决了什么问题？能对应到一个具体动作或判断吗？
- 如果删掉它，用户会因此做错事、卡住、还是毫无影响？
- 用户看它时，**会不会误以为**它是别的意思、别的状态、别的功能？

只有"用户需要 + 不误导"同时成立，才保留。

---

## 2. 用户"该看到"的（信息呈现原则）

只呈现**对当前任务有决策价值**的信息：

- **当前状态要真实可见**：加载中、空数据、出错、部分成功，都要有明确区分，不能一片空白让用户以为"没反应"。
- **结果要可解释**：用户操作后，明确告诉他"成功了 / 失败了 / 正在处理"，并给出下一步。
- **关键数字要带单位与口径**：金额带币种、数量带单位、时间带时区或"更新于 X 时刻"，避免裸数字引发误读。
- **必要的引导与边界**：必填项、格式要求、操作后果（如"删除不可恢复"）要提前说清，而不是等用户踩坑。
- **面向用户的语言**：用用户的业务术语，不用内部代号。

---

## 3. 用户"不该看到"的（信息过滤原则）

以下内容默认**不进界面**，除非用户角色确实需要（如管理员后台）：

- **技术实现细节**：接口名、字段名、SQL、数据库 ID、状态码（200/500）、内部枚举值。
- **报错堆栈 / 调试日志**：开发态信息一律拦截，转成对用户可读的提示。
- **内部术语与黑话**：如"调度任务""worker""缓存命中"等，除非用户是技术人员。
- **与当前任务无关的冗余信息**：同屏塞太多，反而让用户找不到重点。
- **其他人的数据 / 系统内部数据**：严守权限与可见性边界。
- **开发态、测试态标识**：如"测试环境""mock 数据"若必须保留，要做明显但克制的标注，且生产环境必须移除。

**报错处理硬规则**：任何异常，先翻译成用户能懂的话（"导出失败，可能是网络中断，请重试"），并给出下一步动作；**绝不允许**把原始报错直接甩到界面上。

---

## 4. 防误导原则（会不会造成误解）

这是最高优先级，宁可少给信息，也不能给错信息。

- **文案与行为一致**：按钮写"保存"就只保存，写"提交"就不要偷偷做别的；"免费"就不能在下一步收费。
- **状态必须真实**：没成功不能说成功；部分失败不能显示全绿；加载未完成不能显示最终数据。
- **默认值不诱导**：不要默认勾选付费项、不默认开启危险开关；默认项应是"最安全 / 最中性"的那一个。
- **相似元素不制造歧义**：两个长得像但功能不同的按钮（如"导出"和"下载模板"）要在文案或位置上拉开差异。
- **颜色语义统一**：红=危险/错误，绿=成功/安全，黄=警告，不要凭美观乱用，避免用户误判状态。
- **权限与可见性一致**：看不到的功能不要留一个点了报错的入口；无权限就直接隐藏或置灰并说明原因。
- **数字口径透明**：同一页面不要混用不同口径的数字而不说明；环比/同比要标注清楚，避免用户误比。

---

## 5. 执行层硬规则（逐条可检查）

1. 每个新增 UI 元素必须能回答"用户为什么需要它"，答不上来就删。
2. 任何面向用户的文字，都要用非技术人员的语言重写一遍，再看懂不懂。
3. 所有报错路径必须有"用户能懂的提示 + 下一步"，禁止原始异常上屏。
4. 所有状态（加载 / 空 / 错 / 成功 / 部分成功）都要有独立且明确的视觉表达。
5. 凡是"看起来能点"的元素，点了就必须有符合预期的结果或明确反馈；不能点的要置灰或隐藏。
6. 默认值必须是中性/安全项，不得替用户做有风险或付费的决策。
7. 数字必须带单位、带口径、带时间标记，裸数字不上屏。
8. 内部 ID、状态码、技术字段一律不外泄给普通用户。
9. 同屏信息做优先级排序，核心操作与核心数据一眼可见，次要信息可折叠。
10. 交付前用第 6 节自检清单逐条过，任何一条"会误导用户"都必须改掉。

## 6. 交付前自检清单（逐条打勾）

- [ ] 界面上还有没有只有开发才懂的词 / 字段 / 数字？
- [ ] 报错时用户能不能看懂并知道怎么做？
- [ ] 加载中、空数据、出错三种状态是否都有明确呈现？
- [ ] 有没有"假装成功"的地方（异步没回来就显示完成）？
- [ ] 默认勾选 / 默认开关有没有替用户做风险或付费决策？
- [ ] 两个相似按钮 / 入口会不会被用户认错？
- [ ] 颜色有没有用错语义（红绿黄乱用）？
- [ ] 数字有没有单位、口径、时间，会不会被误读？
- [ ] 没有权限的功能是隐藏了还是留了个会报错的入口？
- [ ] 这个页面，一个第一次用的用户能不能不看文档就完成主任务？
