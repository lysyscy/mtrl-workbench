# 前端设计守则 · 以使用用户为中心

> **读者**：修改或审计本项目前端的 agent 与接手者。
> **回答什么问题**：怎样把使用问题改到位，以及怎样判断操作和外观都已合格。
> **何时读**：改布局、控件、交互、颜色、文案或处理显示问题之前；先读 §0，再按 §9 查相关规则。
> **状态**：现行前端口径的唯一主人；基础规则来自用户 2026-09-26/27 裁定，执行重构与紧凑取向经用户 2026-10-08 确认（TAIL-254）。

## §0 怎么用：从使用问题到交付

**你是替"使用用户"把关的人，不是替开发自己方便的人。** 本系统面向熟悉业务的材料科使用者；文案的具体判法回 `.codebuddy/work/40-decisions/D29-文案审计口径-以熟手为准.md`。

每次 UI 小修按下面五步执行。用户只需描述问题；普通尺寸、间距和实现细节由 agent 判断。

| 步骤 | 做什么 | 何时算完成 |
|---|---|---|
| 1. 理解目标 | 将用户描述转成“现象 → 要完成的动作 → 要保持的体验”，用一句话说明目标。用户提出的“大一点／挪一下”是方案线索，结合问题判断是否合适。 | 能说明用户怎样更顺利完成任务；涉及业务含义先查主人文件。 |
| 2. 确定范围 | 根据 §1 判断元素与信息的用途，按 §9 取相关规则；查看当前画面和共用构件。 | 已明确哪些页面、构件与状态受影响，不把局部问题直接等同全站改版。 |
| 3. 选择方案 | 按 §2.9 的取向选择最小必要调整；可同时协调同一构件的尺寸、留白、对齐和状态。 | 方案能解决问题并保持可读、协调；业务行为、操作流程或整页风格取舍未定时，给事实和推荐，请用户决定。 |
| 4. 修改与核验 | 操作核验和视觉核验并行考虑；按 §5 对应执行条及 §6 检查真实界面。 | 相关操作正常，默认与相关变化状态均协调；能点到只是操作证据，截图生成只是取证。 |
| 5. 交付 | 简述改了什么、看了哪些状态、实际检查结果和未验边界；证据留当前票或既定产物位置。 | 功能与视觉均有依据。发现明显留白、挤压、错位或新遮挡，继续调整；无法验证的部分明确标为未验。 |

日常流程、测试选择与运行命令回 `ops/agents/issue-tracker.md` §四及 `.codebuddy/memory/IDE-细节.md` §十一；本件只定义界面要求。按实际影响核验，小修不要求逐条输出问卷、长日报或新增永久测试。新增／修改判据时按仓内流程补隔离反向灵敏度。

条号是稳定引用：既有 §1–§5 条号保留；规则在 §1–§4 定义，§5 只写执行和检查。条目强制力：**必需** = 不符合即缺陷；**应当** = 默认遵守，偏离说明具体理由。机器检查保护部分后果，视觉判断仍由 agent 完成，不能用测试通过代替。

## §1 判断元素的用途

新增、删除或重新组织信息时使用四问；纯尺寸修正可合并在 §0 的目标与范围说明中。

| 编号 | 问什么 | 如何处理 | 检查 |
|---|---|---|---|
| §1.1 | 使用用户需要感知这个元素吗？ | 业务操作与决策需要的保留；排障信息放在对应排障区域。 | 实际任务与角色走查。 |
| §1.2 | 它帮助完成哪个动作或判断？ | 能指出用途再增加；视觉分组、间距和对齐以降低识别成本为用途。 | 目标与画面对照。 |
| §1.3 | 删除它会做错、卡住，还是没有影响？ | 保留必要能力与提示，删减重复信息；保持操作后的反馈。 | 任务走查与相关状态。 |
| §1.4 | 用户会把它误认成别的功能或状态吗？ | 按 §4 区分相似入口、颜色、状态与数字口径。 | 对照实际操作和显示。 |

## §2 用户该看到的内容与布局

| 编号 | 要求 | 常见反例 | 适用边界 | 检查 |
|---|---|---|---|---|
| §2.1 | 必需：加载、空、错误、部分成功的状态真实可见。 | 未加载就画空表。 | 只检查此次触达的状态。 | `backend/tests/test_ux_states.py`；真机相关状态。 |
| §2.2 | 必需：操作后能看懂结果与下一步。 | 处理中说已完成。 | 成功后无需后续动作时，不硬加指路。 | 真实回执与操作走查。 |
| §2.3 | 必需：关键数字带单位、对象和必要的时间口径。 | 裸金额；未知值显示成零。 | 表格单元格可由明确列名承担单位。 | `backend/tests/test_ux_numbers.py`；业务口径核对。 |
| §2.4 | 必需：必填、格式和重要后果在需要决策的位置可见。 | 删除后才说明不能恢复。 | 已由控件明确表达的要求，按 D29 减少复述。 | 控件、校验与后果走查。 |
| §2.5 | 必需：使用业务术语。 | 字段名、内部代号作为标签。 | 专门排障区域保留所需技术信息。 | D29；`backend/tests/test_ux_text.py`。 |
| §2.6 | 应当：需要数量判断时提供可靠统计。 | 让人自己数异常行。 | 只显示有决策价值的数，并核对统计成本与口径。 | 对照统计与对象。 |
| §2.7 | 必需：结论贴在对应行、格或对象上。 | 页头说有异常，表内却没有标记。 | 整批总评可放顶部。 | `backend/tests/test_imp_shell.py`；对象标记走查。 |
| §2.8 | 必需：需处理的异常与正常跳过用不同颜色、不同词并分别解释。 | 合计行和非法数据同色同词。 | 只有一类时不硬造分类。 | 行级标记、图例与计数对照。 |
| §2.9 | 必需：默认采用紧凑的业务工作台布局，兼顾可读性、视觉层次和操作舒适度。[补·2026-10-08] | 为展开控件永久撑高弹窗，收起后留下大块无用途空白；靠缩小字号消除拥挤。 | 留白服务于分组、阅读或操作；长表与编辑器可保留有用途的工作区域。 | §5.14 的真实画面核验。 |

§2.9 的具体判断：尺寸随当前内容和任务需要，间距按信息分组，标签与控件对齐，主次操作清楚；沿用当前风格与共用构件。浮层应完整可见并可操作，展开和收起都协调。局部修正可联动同一构件的明显视觉问题；业务行为、操作流程或整页风格变化按 §0 第3步处理。

| §3.7 | 必需：失败提示说明发生什么、接下来怎么做。 | “Error 500”。 | 排障原文用途回 D29 §六。 | `backend/tests/test_ux_errors.py`；相关造错路径。 |

## §4 防止误导

| 编号 | 要求 | 常见反例 | 适用边界 | 检查 |
|---|---|---|---|---|
| §4.1 | 必需：名称和提示与实际行为一致。 | 按钮叫导出，实际修改数据。 | 能力是否存在以真实实现和业务主人为准。 | 实际操作与回执。 |
| §4.2 | 必需：成功、失败、处理中与部分成功如实表达。 | 没写入就说已完成。 | 与 §2.1 的状态呈现配合。 | 真实回执；`backend/tests/test_ux_states.py`。 |
| §4.3 | 必需：默认值中性、安全。 | 静默选中第一个项目。 | 已确认的业务默认按业务主人执行。 | 初始值与提交后果。 |
| §4.4 | 必需：相似入口可辨，同类构件保持一致。 | 相反动作同名同款；同一选择器各页各造。 | 不同用途用位置、标签与分组区分。 | `backend/tests/test_ux_buttons.py`；共用构件走查。 |
| §4.5 | 必需：颜色承担统一语义。 | 预告用成功绿；说明用风险黄。 | 成功绿只用于已经做完的成功结果；警示黄只用于风险／禁止项；错误与危险用红；普通说明用中性样式。 | `backend/tests/test_ux_colors.py`；状态与颜色对照。 |
| §4.6 | 必需：可见入口可操作，不可用状态有明确理由。 | 浮层或提示遮住按钮；置灰无解释。 | 权限隐藏或禁用按业务主人执行。 | 点击命中与相关状态。 |
| §4.7 | 必需：同一对象的名称和数字口径一致。 | 候选名与选中名不同；两处合计含义不同。 | 不同口径必须就地辨明。 | 显示出口与真实数据对照。 |

| §5.10 | 完成 §6 受影响项的操作和视觉验收。 | §1.4 §2.9 §4.6 | 修改范围及共用构件真实调用者。 | 实际结果与未验边界。 |
| §5.11 | 字号和间距按用户界面档位即时生效。 | §2.1 §2.9 | 沿用 --fscale，倍率来自配置；按用户保存与隔离，首屏与设置入口一致；浏览器缩放不能作为唯一出路。 | `backend/tests/test_ui_scale.py`；触达布局的放大态。 |
| §5.12 | 项目／实体选择沿用共用面板 projPanel。 | §4.4 §4.6 | 弹窗内按现有裁剪例外使用原生 select；改为 .tw 外的栏内展开区后恢复共用面板。其它枚举 select 不在此限制内。 | `backend/tests/test_ux_pages.py`；相关展开和点击。 |
| §5.13 | 卡头操作与状态放在右侧工具区 .sp。 | §4.4 §2.7 | 同卡操作按用途分组，名称可辨，开合有状态反馈。 | `backend/tests/test_ux_pages.py`；默认与开合画面。 |
| §5.14 | 核验尺寸、留白、对齐和状态协调。[补·2026-10-08] | §2.9 | 布局、浮层、面板、弹窗与相关缩放。 | 下述视觉核验。 |

**§5.14 视觉核验**：

1. 看当前使用环境中的实际画面；布局或交互修改，至少检查默认状态和本次触达的变化状态。例如弹窗检查未展开、展开、收起；结果卡检查有结果与相关空／错态。
2. 对照改前问题与改后目标，判断留白是否有用途、字号是否舒适、分组和对齐是否清楚、主次操作是否可辨，以及有没有挤压、遮挡或错位。发现问题继续调整。
3. 改到尺寸或浮层布局时，检查当前视口与界面放大态；有窄屏或缩放证据时补对应边界。共用构件覆盖其受影响调用者，普通文案修正不附带全站截图。
4. 在结果中简述看到的状态与判断依据；截图作为证据按需保存，存在明显问题的画面不算验收通过。无需每次让用户先批准像素方案。

## §6 交付前自检

按当前影响选择条目；每条都要有实际依据。未触达项不扩大核验，未验项如实说明。

| 影响 | 完成条件 | 回查 |
|---|---|---|
| 布局／尺寸 | 内容紧凑可读，分组与对齐清楚，无无用途的大块空白、挤压或错位。 | §2.9 §5.14 |
| 开合／浮层 | 默认、展开、收起均协调；需要的控件完整可见并能操作。 | §4.6 §5.5 §5.14 |
| 操作／默认 | 名称、默认值、禁用理由与实际后果一致。 | §4.1 §4.3 §4.6 |
| 状态／结果 | 相关状态真实，操作结果和下一步清楚。 | §2.1 §2.2 §4.2 |
| 文字／说明 | 熟手能理解系统行为；冗余与排障信息各回合适位置。 | §2.5 §3；D29 |
| 标记／颜色 | 对象有对应标记，异常与正常跳过可辨，颜色语义正确。 | §2.7 §2.8 §4.5 |
| 数字／数据 | 单位、对象、范围、名称与真实结果相符。 | §2.3 §4.7 |
| 共用件／缩放 | 受影响调用者与界面档位仍可读、可操作。 | §4.4 §5.11–§5.13 |

## §7 案例：用来识别问题

| 场景 | 不合格 | 合格 | 回查 |

| 控件放大后拥挤 | 只验标准档，或缩小字体掩盖问题。 | 保持舒适字号，调整布局并看相关放大态。 | §5.11 §5.14 |
