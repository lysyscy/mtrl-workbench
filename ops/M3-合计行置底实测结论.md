## 一、先把「置底」拆成两条 —— 这是本次最容易混的地方

| # | 含义 | 靠什么实现 | 归属 |
|---|---|---|---|
| ① **数据序置底** | 合计行排在数据行**之后**，且**不参与排序** | 渲染时把合计行放最后 ＋ 排序函数的 `pinned` 谓词（`data-pin="1"`） | **代码可保证、可断言** |
| ② **视口吸附置底** | 长表滚动时合计行**始终贴在容器底部可见**，不必滚到底 | **只能靠 CSS** `position:sticky` | 布局效果由真实浏览器探针验证；CSS结构由test_page_shell/test_theme守护 |

> ⚠️ 用户要的是 **②**：**不论何时都显示在容器最底下**。原型目前**做不到**。

## 二、四种写法的真实浏览器实测（`tools/audit/sticky_probe.py`）

**条件**：容器 `.tw` 高 200px（`max-height`）· 表内 30 行数据（内容高 992px）· `scrollTop = 0`。
**判据**：合计行是否已落在容器可视区内（`合计行底 − 容器底 ≈ 0` = 吸附生效）。

| 写法 | CSS 作用对象 | 合计行底 − 容器底 | 结论 |
|---|---|---|---|
| **A** | `tbody tr.sumrow > td { position:sticky; bottom:0 }` ← **原型现写法** | **+792.5px** | ❌ **不生效**（合计行在屏幕外，必须滚到底才看得见） |
| **B** | `tfoot td { position:sticky; bottom:0 }` | **+792.5px** | ❌ 不生效 |
| ~~F~~ | `tfoot td` sticky ＋ `border-collapse:separate` | +793px | ❌ 不生效 |
| **D** | **`tfoot { position:sticky; bottom:0 }`（整块）** | **−1px** | ✅ 生效（单张表） |
| **E** | **`tbody tr.sumrow { position:sticky; bottom:0 }`（行自身）** | **−1px** | ✅ **生效（本工程采用）** |
| **C** | 布局法：滚动区只包数据行，合计行放在滚动区**之外** | −1px | ✅ 生效（但需两张表；列宽要靠 `table-layout:fixed`+`colgroup` 才对齐，实测可对齐） |

**根因**：`position: sticky` 作用在 **`<td>`** 上时，它的**包含块是表格行**（`<tr>`），而行高 = 单元格高
⇒ **没有可位移的空间** ⇒ sticky 永不生效。把 sticky 移到 **行（`<tr>`）或行组（`<tfoot>`）** 上，
包含块变成表格 / 行组区块，才有位移空间。**A / B / F 三种写法全废，都栽在这一条上。**

> ⚠️ 原型 `demo` 里的注释（「合计行由 `sumrow` 钉在表尾」）**与实测不符** —— 那条规则从未生效过，
> 只是"数据序置底"（①）成立，让人误以为 ② 也做了。

## 三、本工程的落地（已实现）

**契约**（`backend/app/mod03_notice/page.py::STICKY_BOTTOM_CSS`，随页面一起提供）：

```css
.dt tbody tr.sumrow{position:sticky;bottom:0;z-index:2}
.dt tbody tr.sumrow>td{background:var(--sf2);box-shadow:inset 0 1px 0 var(--bd)}
```

- 渲染器把合计行输出为 `<tr class="sum sumrow" data-pin="1">`（**`sumrow` 落在 `<tr>` 上** = 写法 E）。
- ⚠️ `z-index:2` 与 sticky 表头同级，但一在顶一在底，不会重叠。
- ⚠️ 吸附行**必须有不透明底色**，否则数据行会透出来。

## 四、例外：什么时候**不要**吸附

| 场景 | 参数 | 理由 |
|---|---|---|
| **分组表**（如 `MOD-07` 焊材/气体提取） | `summary_sticky=False` | 分组合计要**紧贴本组**；两行同时 sticky 会叠在一起 |
| **分段表**（如 `MOD-06` 按「总求和」四段加竖线分隔） | `summary_sticky=False` | 分段视觉要求合计行**原地待在分段末尾**，被吸附会**切断分段线** |

⚠️ **关掉吸附 ≠ 关掉置底**：`summary_sticky=False` 时仍然 `data-pin="1"`（数据序照样钉在表尾、不参与排序）。

**分段线怎么做**（`MOD-06` 的处置，替代原型"手写 `<tr style=…>`"的绕法）：
`columns[i]["vsep"] = True` 标记**段首列** ⇒ 渲染器对 **表头 / 数据行 / 合计行 / 总求和行四处**
用**同一个 `<td>` 出口**加 `class="vsep"` —— 结构上不可能漏。
> 原型 `MOD-06` 当年是**手写 `<tr style="background:…">` 绕开了 `sumRowOf`**（用户 2026-09-15 说明：
> 当时没给 `sumRowOf` 加"框线调整"能力）⇒ 那行既拿不到 `sumrow`（不吸附）、也不在统一出口里（易漏）。
> **本工程不允许绕开出口**：分段线与吸附都由渲染参数表达。

## 五、历史纠正（2026-09-16；32变量为当时形态，当前真源回page.py）：这两条规则**曾静默失效** —— 因为**变量没有定义**

**发现**：`STICKY_BOTTOM_CSS` / `VSEP_CSS` 是**照 `delivery/demo/` 原型抄的**（连 `var(--sf2)`、`var(--bd)` 都照抄了），
但**没有抄原型的 `:root`**（原型第 9–21 行有完整变量表）⇒ **变量无定义** ⇒ 按 CSS 规范这类声明
在**计算值阶段整条失效**、且**不报错** ⇒ **合计行吸附底色 / 内阴影 / 分段竖线全都不显示**。

⇒ 也就是说：**本文档 §三「本工程的落地」当时只落了「规则」，没落「变量」** —— 规则在、效果不在。

**顺带纠一处抄错**：`VSEP_CSS` 原本写的是 `var(--bd2)`，而**原型第 94 行用的是 `var(--bd)`**（主边框）。

**修法（2026-09-16 落地）**：
- 新增 **`page.THEME_CSS`（32 个变量，命名照原型）= 全站唯一主题真源**；
  `BASE_CSS = THEME_CSS ＋ 基础样式` ⇒ 引用 `BASE_CSS` 的 **8 处自动获得变量定义**（防漏设计）；
- 三个静态页改为 `<link href="/static/theme.css">`（返回**同一个常量**）；`VSEP_CSS` 的 `--bd2` → `--bd`（照原型）；
- **防回归自检** = `backend/tests/test_theme.py`：断言"这两条规则用到的变量都已定义"＋"全工程 CSS 不得再出现色值字面量"。

> ⚠️ **教训（凡"从原型 / 别处搬规则"的场合都适用）**：**搬规则时必须同时搬它依赖的变量定义**。
> 反过来更值得记：**变量未定义造成的失效是静默的** —— 不报错、不崩、只是不生效 ⇒ 只能靠
> **实测（§二 的 `sticky_probe.py`）+ 自检**抓出来。本次正是先实测到"改前 = +792.5px"，才追到根因。
