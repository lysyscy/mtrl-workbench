## 一、结论（一句话）

⭐ **成品 = 以「用户手作的那份成品 xlsx」为基底，做 `zipfile` 字节替换** —— 不改 i8 导出件、也不用 openpyxl

**六处替换 ＋ 一处必须自己重建**（`common_tpl.rebuild()` 的步骤，逐条对应 `xl/` 内文件）：

| # | 目标 | 做法 |
|---|---|---|
| 1 | `xl/sharedStrings.xml` | 保留模板全部字符串，**追加**本月新串 |
| 2 | 数据 sheet（`xl/worksheets/sheetN.xml`） | 表头行**保留模板原样**；数据行按模板 `style_row` 的**列样式**生成 |
| 3 | `xl/pivotCache/pivotCacheDefinition1.xml` | 各字段 `sharedItems` 按本月数据**增补**；`recordCount` / `ref` 改写 |
| 4 | `xl/pivotCache/pivotCacheRecords1.xml` | 记录**整体重建**（每格 = 该字段 sharedItems 的下标） |
| 5 | `xl/pivotTables/pivotTableN.xml` | `location` / `axisRow` 的 `items` / `rowItems` 随**仓库集合**动态 |
| 6 | 同上 | 置 **`refreshOnLoad="1"`**（⚠️ 唯一合法位置 = `pivotCacheDefinition`，见 §六） |
| 7 | **两张透视所在的 sheet**（`sheet1/2.xml`） | ⭐⭐ **必须自己重建「显示区」** —— 那是 Excel 存下来的**静态渲染值**；⚠️ **`refreshOnLoad` 顶不了它**（它只保证刷新**缓存**）。详见 §六 末尾「`TAIL-43`」 |

## 八、透视的「显示区」（`TAIL-43` 的定性与修法 · 2026-09-18）

### 8.1 真根因（**已定性**，⛔ 不是"`refreshOnLoad` 没生效"这么简单）

模板法原先只重建「数据 sheet ＋ 缓存 ＋ 透视定义」，**不重建透视的显示区** —— 即
`xl/worksheets/sheetN.xml` 里由 Excel 保存下来的**静态单元格值**（= 上次渲染结果）。
本月数据**比模板少**时，透视的 `location` 随之**收缩**，模板的旧渲染行就落到了新 `location`
**之外** ⇒ **任何应用都不会去清它们**。

**真机实证（Excel 打开成品读单元格）**：

| 现象 | 实测 |
|---|---|
| `过程资料` | `location` 由 `A3:N14` **长到** `A3:N15`（仓库 7→8）⇒ 旧行**恰好在**新区域内 ⇒ 被重画 ⇒ **看起来是对的** |
| `安全文明施工费` | `location` 由 `A3:B9` **缩到** `A3:B4`（本月该费用 0 个仓库）⇒ Excel 只重画 `A3:B4`（写出「总计」空行），**`A5:B9` 的模板旧值（邵武 460 / 太康 40336.35 / 总计 64251.85）原样留着** ⇒ 用户读到的是**上个月**的数 |

⇒ **同一个缺陷，只在 `location` 收缩的那张上暴露**（这就是为什么之前只发现了「安全文明施工费」那一张）。

### 8.2 三条候选根因的裁定（逐条实测，别选一条就动手）

| 候选 | 裁定 | 依据 |
|---|---|---|
| ① 应用**是否真会**按缓存重绘 | ✅ **会**（缓存侧没问题） | Excel 实测：`过程资料` 的 `B7` = **17939.35**，与「从成品缓存独立复算」的值**逐分相同** |
| ② `refreshOnLoad` 的实际生效条件（要不要配 `invalid="1"`） | ✅ **不需要配 `invalid`**；⚠️ 但该属性**只管刷新缓存**，**不清 `location` 之外的残留** | ECMA-376 / `CT_PivotCacheDefinition`：**"refresh the cache when the workbook is loaded"**；位置实测唯一合法 = `pivotCacheDefinition`（§六） |
| ③ 我们生成的 `pivotCacheRecords` 是否被严格解析接受 | ❌ **被接受、且渲染正确** ⇒ **这条排除** | 实测：`报表1`(写出前的明细) → 缓存 → 显示区 **三路逐格一致**；且与 Excel 自己渲染的值相同 |

⭐ **教训（与本仓已有的通法同族）**：**「自己解析自己生成的 XML」查不出这类问题** ——
原对账的两端都来自我们自己的产物，而病在**第三方应用如何对待区域之外的旧单元格**。

### 8.3 修法（本仓实现）

1. **自己重建显示区**（⛔ 不依赖"打开即刷新"是否被应用认）：
   `sheet_display.render_pivot_sheet()` **整块换掉 `<sheetData>`** ——
   ⭐ 关键是**「新显示区之外一格都不留」**（这正是清僵尸行的动作），表头行与页筛选行**原样保留**。
2. **口径一律从模板读**（⛔ 不在代码里另抄一份）：列序 =〔每方向：各分组… ＋ 该方向汇总〕… ＋ 总计；
   分组映射 = `cacheField` 的 `<fieldGroup base><discretePr>/<groupItems>`；
   页筛选选中项 = `axisPage` ＋ `multipleItemSelectionAllowed="1"` ＋ `<item h="1">`（**隐藏 = 未选中**）。
   ⚠️ 页筛选**不许**改写成 `<pageField item="N"/>` —— 那是**单选**语义，与模板存法不同。
3. **该格没有匹配记录 ⇒ 不写**（⛔ **不写 0** —— 0 会被读成「确实为 0」，与「这个月没有」是两回事）。
4. **新增第二道对账**：「**显示区 vs 缓存重算**」（`verify_display`）——
   专抓两类病：**① 新显示区之外还有行**（僵尸旧值）· **② 格子里的数与缓存对不上**。
5. ⚠️ 顺手修掉一处**顺序不确定**：模板里没有的新仓库原先按 `set` 迭代顺序排（字符串哈希随
   `PYTHONHASHSEED` 变）⇒ 现在它**直接决定显示区每行的位置** ⇒ 改成**按首次出现**。

**验证（可复跑）**：`tools/_verify_tail43.py`（22 项）· `backend/tests/test_tail43_display.py`（10 条）·
反向灵敏度 `tools/_mut_tail43.py`（6 处变异全部让对应断言变红 · MD5 逐字节复原）。

### 8.4 收发结存那份（**同一个模板法，一并复核**）

`收发结存` 的总表 `Sheet1` **就是它的显示区**。它**原实现已经会写显示区**（用 `openpyxl` 逐行写
仓库 ＋ 4 个金额）⇒ 2026-09 **没暴露**（当月仓库 8 个 > 模板 7 个，行是"长出来"的，没有旧行残留）。
但它**只写新行、不清旧行** ⇒ **仓库变少时同样会残留模板旧值**（潜在缺陷，同族）。
⇒ ✅ 已补：写完后**删掉新显示区之外的行**，并在 `verify()` 里加**「显示区之外不许再有行」**守卫。

| 出口 | 干什么 |
|---|---|
| `locate_data_area` | 认**标记文字**定位数据区；终点 = 第一个「**回指数据区**」的汇总公式行（其区间跨多行且起于首行） |
| `fill_sheet` / `fill_workbook` | 样板数据区对齐到 n 行（**保留首行当样式母版**）→ 写值 → 尾块按 offset 平移 |
| `verify_filled` | **第二道对账**（读回产物 vs 调用方给的期望值）：逐格 / 位置 / 残留 / 公式 |

**三条硬性**：① 认文字**不抄坐标**；② 尾块随行数派生；③ **新数据区之外一格不留**。

### 9.2 三个实测坑（都踩过，别再踩）

1. ⭐ **`insert_rows` / `delete_rows` 不搬合并区**（实测 openpyxl 3.1.5）—— 值与样式会搬、
   **合并区不会** ⇒ 尾块的合并（如过程资料的 `A14:R15`）必须自己按 offset 平移（`_shift_merges`）。
2. ⭐ **`delete_rows` 留下空的 `<row>` 元素** —— `dimension` 是对的，但 **Excel 的 `UsedRange` 会多算几行**
   （实测：内容只到 `A1:O4`，而 `used=A1:O9`，用户看到数据下面还空着 5 行、也会进打印范围）
   ⇒ 填完必须**清掉末行以下的行属性**（`_trim_row_dims`），并把这条**加进守卫**。
3. ⭐⭐ **`verify_filled` 必须读两遍工作簿**：`data_only=True` 只给值（公式格读成 `None`）、
   `data_only=False` 才看得到公式 —— 只用前者时「还有公式」那条**永远不会报**（死代码，比没有还坏：
   它让人以为查过了）。

### 9.3 一条**守卫主动拦下的错**（留着这个设计）

尾块里**我方没覆盖**的格出现**公式或数字** ⇒ 引擎**拒绝产出**。
实测：写 0 行的边界样本时，尾块上移到第 2 行、模板原第 9 行的 `=SUM(D2:D8)` 变成 `D2`，
而那份 spec 只覆盖了 C / O 两列 ⇒ **当场报错**。
**这正是它存在的理由**：汇总值必须由调用方**算好后给**，⛔ 不许留一个"算不出来 / 算的是别的区间"的公式。

### 9.7 片 4a：模板法**引擎**被真机抓出两处真 bug（2026-09-18 · 都在 `tpl_fill`）

> 背景：清单 §四-5 早写着「引擎的合并区平移到片 4a 才第一次真用上」—— **实测果然有两处从没被走到过**。
> ⚠️ 两条都属「**没运行过的代码路径**」，而且**台账 / 焊材那两片永远走不到**（它们的尾块里没有合并区）。
> ⭐ 通法：**"这一片第一次用上某条能力"= 那条能力要按"从没跑过"对待** —— ⛔ 别因为"引擎早就写好了"就免验。

1. **`_shift_merges` 不能用 `ws.unmerge_cells(str(rng))`** —— 它会对区间里**每一个**格执行
   `del self._cells[(row, col)]`，**不管那格有没有被创建过** ⇒ 撞上"从没被访问过的影子格"就抛
   `KeyError: (r, c)`（实测：过程资料 `Q13:R13` 的 `R13` ⇒ HTTP 500）。
   ⇒ 改法：**直接改 `merged_cells.ranges`**（新旧范围增减，纯几何登记）。
   ⭐ 通法：**合并区的"几何"与"单元格本体"是两套账** —— 挪位置只该动前者。
2. ⚠️ **"空行壳"有两种，`_trim_row_dims` 原先只清一种** ——
   ① `delete_rows` 搬走值/样式后留下的空 `<row>` 元素（原有覆盖）；
   ② **模板里本来就有 `<row>` 元素、没有值的空行**（过程资料模板 `R16~R18` 就是）——
   它们会跟着 `delete_rows` **上移**成"**有行无值**"的壳 ⇒ 真 Excel 的 `UsedRange` 报 `A1:R11`
   （内容只到第 8 行；用户看到"数据下面还空着几行"、还会进打印范围，与 `TAIL-43` 同族）。
   ⇒ 改法：先 `delete_rows` 把末行以下整段删掉、再清行属性；
   并给 `verify_filled` 加一条 **③c `max_row > 末行`** ⇒ 这类病灶以后**产物自检就会报**（⛔ 不再只靠真机肉眼）。
3. 顺带把「**写文本前先设文本格式**」从 `ledger_export` **提到引擎**（`tpl_fill.set_text_format`）——
   同一个坑的第二次出现（台账「月份」列 / 过程资料「时间」列）。
